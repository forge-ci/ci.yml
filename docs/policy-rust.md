# Rust repository CI policy

Apply this policy with the [general code repository policy](policy-general.md). Classify each Rust repository by the artifacts it ships. A workspace can contain both libraries and applications, and should satisfy both relevant subsections.

The reference implementation is [`zackees/template-python-rust-cmd`](https://github.com/zackees/template-python-rust-cmd), the `rust-pypi-app` profile built out round by round in [issue #6](https://github.com/zackees/ci.yml/issues/6) and checked by [`ci_lint`](../ci_lint/) against `ci.toml` schema 3 ([docs/ci-toml.md](ci-toml.md)). The "Status" column in each rule table below reflects what `ci_lint` actually checks today, verified against its source as of zackees/ci.yml@`12a426d` (round-5, PR #24); a rule marked **candidate** is fleet policy that no checker enforces yet.

## Rules for every Rust repository

- The quick `ci.yml` gate runs the repository's declared formatting, compile-bearing lint, and focused test checks on Linux. Use `zackees/setup-soldr` to provision Soldr and run compile-bearing Rust checks through Soldr where the dependency graph permits it. Flag pinned manual Soldr downloads or installs without `setup-soldr` for review; a pin by itself is not a defect.
- When a repository uses Dylint, run the intended workspace lint set once on Linux through Soldr. `soldr cargo dylint --all --workspace` is a reference form; `soldr dylint` or another Soldr form is acceptable when its arguments and observed coverage are equivalent. Direct `cargo dylint`, compiling `cargo-dylint` or `dylint-link` during each job, and duplicate native Dylint jobs are violations unless an approved exception explains them.
- Verify that the Linux lint job exercises platform-specific lint cases that the repository intends to enforce. Install the pinned nightly `rust-std` components for checked targets, and confirm the actual target checks. A Linux runner alone does not prove Windows or macOS source coverage.
- Keep Dylint driver, library, and output cache identities consistent with the toolchain identity used by Soldr and `setup-soldr`. A passing lint result must not silently skip saving reusable outputs. Do not copy restored files over read-only cache trees. Measure cold new-commit runs separately from warm exact-commit reruns.
- `cargo fmt` is formatting rather than a compile-bearing lint. Clippy, if required by the repository profile, is a separate check and should use Soldr. Do not interpret the Dylint rule as permission to omit Clippy or formatting.
- Bound function complexity in the clippy run (`RUST-018`): `[workspace.lints.clippy]` sets `cognitive_complexity` and `too_many_lines` to `warn` (clippy runs with `-D warnings`), every member inherits it, `clippy.toml` keeps the default thresholds, and each function already over them carries `#[expect(..., reason = "...")]` -- never `allow`. Lint every target triple whose cfg-gated code the repository ships, or a Windows/macOS-only function escapes the ceiling.
- Guard the async boundary (`RUST-019`, [issue #413](https://github.com/zackees/ci.yml/issues/413)): `[workspace.lints.clippy]` sets `await_holding_lock`, `await_holding_refcell_ref` and `await_holding_invalid_type` to **`deny`**, every member inherits them without re-declaring one weaker, and `clippy.toml` registers the repository's **own** blocking wrappers under `await-holding-invalid-types` with a reason each. The std `std::sync`/`std::cell` guards need no registration -- the two built-in lints already cover them, which is what soldr#3856's `clippy.toml` records (the #413 draft's std-path list is superseded by that implementation evidence: soldr registers only its wrappers). A synchronous lock or `RefCell` borrow held across `.await` can deadlock the runtime, and all three lints sit in the `pedantic` group, so nothing fires until a repository opts in here. `large_futures` stays warn/measurement first -- a size threshold needs a measured baseline before it gates (**Candidate**). Prior art: [fbuild#1688](https://github.com/FastLED/fbuild/pull/1688) (proposal, open -- not merged); adoption: [soldr#3856](https://github.com/zackees/soldr/issues/3856) done, [zccache#1979](https://github.com/zackees/zccache/issues/1979) open. Spike + hazard repro evidence on #413 (2026-10-25): zero offenders in current soldr code at toolchain defaults, and a pinned-clippy 1.95.0 repro diagnosing both the MutexGuard and RefCell shapes while the corrected function passes.
- Keep full native platform builds and tests where they protect real behavior, but place them outside the quick `ci.yml` gate and declare whether they block merges.
- For distributed native Linux apps, prefer musl and build musl artifacts by default for supported architectures. Add glibc 2.17 compatibility artifacts wherever the dependency/toolchain graph permits; an infeasible target needs a scoped central exception. Prove the glibc symbol floor and compatible runtime behavior, and prove musl linkage/runtime behavior. A Linux runner or successful Cargo build alone does not establish artifact compatibility.
- Declare supported Windows artifacts by both architecture and ABI. GNU and MSVC, and x64 and ARM64, are independently verified variants; cross-compilation does not prove native runtime behavior. Do not invent unsupported architecture/ABI combinations to fill a matrix.

### All compile-bearing work goes through Soldr; native runners only execute

**Decision:** every declared platform's Rust code compiles once, on Linux, through Soldr; a native Windows/macOS/ARM runner only executes a prebuilt nextest archive and installs a prebuilt wheel -- it never has a Rust toolchain. This keeps toolchain, registry, and compile caches on one host instead of fragmenting them per runner OS, and keeps native jobs short. Mechanically: `TOOL-001` bans bare `cargo`/`rustc`/`rustup`/`cargo-*`/`maturin`/`cross`/`cibuildwheel` anywhere in a workflow `run:` line or a tracked `ci/*.py`/root `*.py` subprocess call, and `CACHE-009` confines every `zackees/setup-soldr` call to one sanctioned wrapper directory with mandatory inputs -- between them these implement `RUST-001`'s mechanical signal today, under those two IDs rather than as a distinct `RUST-001` check. Proven in zackees/template-python-rust-cmd#17/#18/#19 (the setup-soldr wrapper, the fast lane, and tag-selected platform lanes cross-built on Linux and executed on native Windows/macOS/ARM runners with no Rust toolchain present).

### Platform code lives only behind the `platforms/` facade, with one selector

**Decision:** every OS-specific line of code lives behind a `platforms/` facade -- the pattern soldr, zccache, and kernal-api already use: one `cfg_select!`/equivalent selector with explicit `windows`/`linux`/`macos` arms (no `_` fallback, no `unix` arm, so an unsupported OS fails to compile), a cfg-free facade module, and native trees only inside `platforms/{windows,linux,macos}/**`. `LAYOUT-001` bans a host selector (`cfg(target_os)`, `cfg(windows)`, `cfg(unix)`, `sys.platform`, `platform.system()`, `os.name`) anywhere outside the declared `[allow].platform-code`/`platform-selector` paths, as a fast static regex scan; the design additionally calls for a pre-expansion Dylint lint (soldr's `ban_platform_cfg_outside_boundary` is the reference implementation, at a zero baseline) to catch what regex scanning can't see after macro expansion -- that Dylint lint is part of the template's Dylint lane (below), not a separate `ci_lint` static rule. Proven in zackees/template-python-rust-cmd#16/#17 (the layout: `crates/template` re-export amalgam, `crates/private/{template-core,template-json,template-platform}`, one selector, and a real `platform_boundary` Dylint lint, proven RED/GREEN).

### Dylint runs once, from one Linux job, for every declared platform

**Decision:** Dylint is the mainline cross-platform lint gate, and it runs for **every** declared target from one Linux job on every PR (issue #6 §2/§3), using the target's prebuilt nightly `rust-std` (never a per-run toolchain build -- see [issue #5](https://github.com/zackees/ci.yml/issues/5)'s `RUST-009`, below) and a catalogued driver-toolchain pin (`dylint-toolchain`). Because it runs on every PR, it must be the fleet's *fastest* lane, not its slowest -- the opposite of what zackees/clud showed (host-only Dylint: 235 s; host + Windows + macOS: 472 s, with **zero** cache layers reused on either run, because a successful run was silently failing to save its own output -- `RUST-004`). The template reproduces and measures this directly (issue #6's Dylint use-case comment, scenarios D1-D8) rather than assuming the fix transfers. Proven in zackees/ci.yml#20/#22 (the cache runtime that makes a Dylint save's success/failure explainable) and zackees/template-python-rust-cmd#18 (setup-soldr v0.9.81 -- fixing setup-soldr#538's Dylint success-marker detection gap -- ingested and measured: 3m49 cold / 2m33 warm before, 2m05 on a new commit / 1m58 on a same-commit rerun after, with the foundation cache hitting on every commit; a multi-target invocation shape beat sequential passes by 23-37%). Round-6E made all three mechanical: `RUST-002` (static -- one Linux job, `soldr dylint`/`soldr cargo dylint` only, no per-run tool builds, no `--workspace` without `--all`), `RUST-003` (runtime, `ci-lint dylint coverage` -- every declared target shows a completed check pass in real job-log/`--results-out` evidence, and an `E0463` rust-std gap is named explicitly), and `RUST-004` (live, extends `ci-lint cache audit` -- a declared `dylint`/`dylint-output` family with no live entry at all on the default branch while its latest run has a successful `dylint` job).

[Issue #9](https://github.com/zackees/ci.yml/issues/9) asked that cached cross-platform Dylint be the `setup-soldr` **default**, not per-repository cache plumbing: `setup-soldr` v0.9.83+'s `dylint-targets` input (`zackees/setup-soldr#544`) runs `soldr dylint prepare --target <t>` for every declared cross target and folds the full target set (host + declared) into the Dylint foundation/output cache-key hashes, so a target-set change gets its own cache generation instead of colliding with an unrelated one. A consumer sets `dylint: true` plus `dylint-targets` (comma-separated triples) and gets warm cross-target `rust-std` with no per-repository prepare loop -- see `zackees/template-python-rust-cmd`'s `ci/dylint.py --print-cross-targets` step, which only resolves the target list from `ci.toml [platforms]` and no longer calls `soldr dylint prepare` itself. This is implementation detail under the existing `RUST-002`/`RUST-003`/`RUST-004` mechanics, not a new rule: `RUST-004`'s live per-family cache-entry check and `RUST-003`'s per-target coverage evidence already cover a `dylint-targets`-based lane the same way they covered the pre-#9 per-repository prepare loop. Not yet in `setup-soldr`: vendoring the MSVC `xwin` sysroot / Apple SDK download ahead of time (issue #9 proposal item 5, still tier-2 downloaded per warm run) and the soldr-side success-marker identity fix between the host-qualified and short nightly channel strings (issue #9 proposal item 3).

### Features are private crates; the shipped crate is a re-export amalgam

**Decision:** a Cargo "feature" is the presence of a small private crate (`publish = false`, no `[features]`, no `cfg(feature)`), not a `cfg`-gated branch inside shared code -- each private crate then compiles exactly once per `(profile, target)`, however many feature combinations the public crate offers, and the fleet never tests a feature-combination matrix. The public/shipped crate is a pure re-export amalgam: `[features] x = ["dep:<private-crate>"]` wiring and `pub use` only, no logic. `RUST-011` checks this statically (a private crate with `[features]`/an optional dependency/`cfg(feature)`; an amalgam feature not of the `dep:` form; `--all-features`/`cargo hack`/an out-of-`[rust].ship` `--features` value) and confirms it at runtime by counting the actual distinct `(features, profile, target)` combinations a build produced (`ci-lint units`) -- a private crate compiled twice with different feature sets, or the amalgam compiled with an undeclared set, fails even when nothing static could see the drift (e.g. Cargo's feature unification splitting across `-p` invocations). Every test binary is declared and size-capped (`RUST-005`/`RUST-012`): `[rust.tests].binaries` is the fan-out budget, checked both against Cargo's autodiscovery rules statically and against the compiler's own artifact records at runtime (`ci-lint tests size`, against `max-binary`/`max-total`). Proven in zackees/ci.yml#11/#13/#15 (the runtime commands: `units`, `tests size`, `wheel check/installed`, `gate`, `--local`, `selftest`).

### Rust build caching goes through setup-soldr; `Swatinem/rust-cache` is banned (CACHE-025)

**Decision ([#209](https://github.com/zackees/ci.yml/issues/209)):** `Swatinem/rust-cache` is banned in every fleet workflow and composite action. Rust build caching goes through `zackees/setup-soldr` (its zccache-backed build cache, which is on by default) or soldr itself (`soldr cargo ...`, `soldr cook`). No step restores or saves `~/.cargo` or `target/` under a hand-chosen key. A Swatinem step duplicates the cache setup-soldr already restores. That cache is keyed on content, lockfile, and toolchain, restores the nearest ancestor (candidate `CACHE-024`, #185), and carries attestation lineage keys (`GATE-010`, [ci-attestations.md](ci-attestations.md)). Swatinem replaces those keys with a `shared-key` suffix bumped by hand (zackees/bosn's `rust-workspace-v1`). It spends the repository's 10 GiB Actions cache budget on whole `target/` trees, the payload class `[cache].never` and `CACHE-007` exist to exclude (soldr#2996 measured 9.76 GiB of it on one repository). A bosn → act local run cannot reproduce it.

**Migration:** delete the step. Confirm the job runs `zackees/setup-soldr@v0` with its cache enabled (no `cache: false`, no `ZCCACHE_DISABLE` kill switch; see `CACHE-010`). A job that does not use soldr yet moves to setup-soldr plus `soldr cargo ...` (`RUST-001`). **No exceptions (maintainer decision 2026-10-02).** Neither a same-line `# ci-lint: allow CACHE-025 <reason>` nor a ci.toml `[[exceptions]]` entry excuses a Swatinem step; an `[[exceptions]]` entry naming `CACHE-025` is itself reported as a `CACHE-025` violation. The two carve-outs the rule first shipped with are gone. A soldr bootstrap job that builds soldr before any soldr exists installs a released soldr through `zackees/setup-soldr@v0` and builds with it, or runs uncached. A benchmark that used Swatinem as its comparison baseline compares against a different baseline, such as no cache or `actions/cache`.

## Objective: coverage-per-compile-minute, not maximum coverage or minimum time

**The tradeoff this policy optimizes.** Compile time and lost coverage trade against each other; the goal is to minimize the downside of lost coverage per compile minute spent, not to run every check on every platform on every PR, and not to strip jobs until CI is merely fast. Without an explicit objective, a repository can drift toward either extreme and still pass the letter of the rules above -- see [issue #5](https://github.com/zackees/ci.yml/issues/5), which raised this gap from live evidence (zackees/clud dropping all cross-target Windows/macOS coverage silently, and separately carrying a stale doc claiming native-OS coverage it no longer ran -- `GEN-010`).

**The tiers, and the bug class each is expected to catch:**

| Tier | What runs | Bug classes it catches | Cost shape |
| --- | --- | --- | --- |
| Cheap, non-codegen checks | Dylint (host + cross-target check-only passes using prebuilt `rust-std`, never built per run), Clippy, `cargo check`, `cargo fmt --check` -- no codegen, no link | Platform `cfg`/API/type/lint errors: code that would not even compile or would clippy-fail on a target it never actually ran on | Linear in source size, not target count; runs on every PR, every target, without ever paying a native runner |
| Linux build + unit | `soldr cargo build`/`test` on the Linux host, through Soldr | Logic bugs the type system and lints can't see, on the one platform every PR actually compiles for real | One compile + link per PR |
| Native runtime tests | A real Windows/macOS/ARM runner executing a prebuilt nextest archive (never compiling) | Platform runtime semantics a cross-target check-only pass cannot see: path/filesystem behavior, process semantics, OS-specific timing -- exactly what zackees/clud#1439's `rm_tool::resolve` parent-dir bug was (clud#1440/#1446 fixed it; the paired Dylint failure in the same incident was a cheap-tier catch, the Windows failure was not) | Bounded by execute-only time; no toolchain, no compile |
| Scheduled/release | Full cross-platform release builds, wheel/artifact verification, perf comparison | Packaging/release-specific regressions (glibc floor, wheel completeness, ABI) that no PR-time tier needs to catch on every push | Off the PR critical path entirely |

**PR selection:** follow [Selecting full PR coverage](policy-general.md#selecting-full-pr-coverage). Shared Rust business logic that calls a platform facade stays on the routine tier; changing the facade's native implementation, OS branch or runtime contract selects the affected native lanes. Moving unchanged platform calls or branches into helpers does not justify `ci-full`.

**The working target is ~90-95%: cheap, non-codegen checks should catch that share of common LLM-introduced Rust bugs**, because those bugs are mostly platform-dependent surface errors (wrong `cfg`, wrong API for a target, a lint Dylint already knows) rather than platform runtime-semantics bugs. This is the owner's stated working target, **not yet a measured fleet number** -- this policy requires measuring it per repository, not asserting it fleet-wide.

**How to measure it.** For a repository, classify every fix PR and every `main`-breaking regression by the *cheapest tier that would have caught it*, then report (cheap-tier catches) / (cheap-tier catches + everything a more expensive tier had to catch). zackees/clud#1439 is the reference fixture for how to do this: its unlabeled-PR merge broke two things at once, fixed separately -- the Dylint failure (clud#1440) is a cheap-tier catch (RUST-002/RUST-003 territory: a lint that would have failed on any target, cheaply), and the Windows unit-test failure (clud#1446, `rm_tool::resolve`'s parent-dir semantics) is a native-runtime catch that no cheap check could have found. One incident, one of each -- exactly the ratio this measurement is meant to produce per repository, not a hand-waved aggregate.

**Moving work between tiers is a coverage decision, not a speed decision.** Removing a native leg or a cross-target check-only pass without an equivalent replacement is a regression (`RUST-008`, [issue #5](https://github.com/zackees/ci.yml/issues/5), candidate) even if it makes CI faster; the policy requires naming which bug class the removed check covered and where (if anywhere) that coverage now lives, matching `AGENTS.md`'s working rule: *"Preserve required lint, test, platform, and artifact coverage when proposing a faster workflow. Confirm coverage from commands and runs, not from a runner label."*

## Rule catalog

| Rule ID | Mechanical signal | Status |
| --- | --- | --- |
| `RUST-001` | Compile-bearing Rust CI bypasses Soldr, or manually pins/installs Soldr without `setup-soldr`, absent an approved dependency exception. | Enforced by ci-lint (static precheck) -- emitted alongside `TOOL-001` (bare cargo/rustc/rustup/maturin ban) and `CACHE-009` (setup-soldr call outside its sanctioned wrapper) as its own `RUST-001` finding (M2-21, ci.yml#44), not only inferred from those IDs; see policy-general.md. **Every Rust repository, `ci.toml` or not (ci.yml#170):** `ci-lint local-gate lint` reports a bare `cargo`/`rustc`/`rustup`/`maturin`/`cargo-nextest` in any workflow/composite-action `run:` line, the local gate's argv and the scripts it names (Python string-literal argv included), and every `bosn.toml` task `cmd` (split on unquoted shell separators only, so `echo "cargo | foo"` is not a bare cargo) -- a Rust project is always driven through soldr, locally and remotely. ## Rust libraries

A library profile covers crates whose primary shipped artifact is an API consumed by another project. The quick gate should check workspace formatting, compile-bearing lint, unit tests, and the public API or documentation tests the project declares essential. Test supported feature combinations in the quick gate only when they fit its timing budget; run broader feature, target, and minimum supported Rust version matrices in separate workflows. Preserve platform-specific tests when the library's behavior depends on them.

Do not require a wheel, npm tarball, or release build from a library that does not publish such an artifact. A crate published alongside a Python or npm package also follows the application package checks below.

## Rust applications published to PyPI and/or npm

An application profile covers a Rust executable or extension delivered to users through a Python wheel, an npm package, or both. In addition to the common Rust checks, the quick Linux gate must test the **installed artifact**, because source-level Cargo tests do not prove packaging works.

For app release coverage, keep `manylinux`/glibc and `musllinux`/musl wheels distinct, and record the libc/ABI of native binaries embedded in npm packages. The proposed release cycle validates the exact staged artifacts before posting them publicly.

### PyPI package

- For a Rust-backed Python package, use Soldr as the `pyproject.toml` build backend when supported. Flag direct Maturin as the build or install backend for review; retain a documented exception where Soldr cannot be used, such as a dependency cycle.
- Build one representative Linux wheel in the quick path, install it in a clean environment, and smoke-test the import, native module, and exposed command-line entry point where present. Run Ruff and Pylint on the Python sources under the general policy.
- Build the full supported wheel matrix and run platform-specific installation tests in separate release or slower validation workflows. Do not publish to PyPI from an ordinary PR.

### Release Linux wheel glibc floor ([issue #19](https://github.com/zackees/ci.yml/issues/19))

1. **Release wheel floor.** Every release wheel for a `*-linux-gnu` target is `manylinux_2_17`, built with `soldr wheel --release`, which enforces the floor through soldr's catalogue glibc-2.17 toolchain -- even when the target equals the build host (zackees/soldr#3432). musl targets are `musllinux_1_2`. A higher floor is a recorded `[[exceptions]]` entry with a reason, owner, and review date, never an accident.
2. **Verify, don't trust the tag.** The release (or release-candidate) workflow checks each Linux wheel's actual glibc symbol requirements against its claimed tag (e.g. `verify_wheel_glibc.py --max-glibc 2.17`, wrapped by `ci/release.py glibc-check`). It fails the job on any mismatch or any floor above policy.
3. **Where to build.** Build Linux release wheels on an x86_64 Linux runner. That host produces both `x86_64` and `aarch64` at 2.17 (aarch64 cross-built through the catalogue); an aarch64 host cannot yet produce a 2.17 wheel for either architecture (soldr#2874), so release Linux wheels never build on an `-arm` runner.
4. **The floor is announced, never silent.** A build against the catalogue toolchain prints an info line naming the floor in use; overriding it (`--host-glibc`) is itself an exception under rule 1 and prints its own info line naming the host glibc the wheel will require. CI must keep that line visible (don't filter soldr's stderr).
5. **Dev and PR builds are exempt.** Quick-gate wheels may use the host glibc; they are for testing the installed artifact and are never published.

`PKG-007` checks this statically against the workflow that drives a release build: a job whose `run:` steps build a `*-unknown-linux-gnu` wheel with `--release` must not run on an arm64 runner, must go through `soldr wheel --release` (or a wrapper calling it) rather than a bare `maturin ... --zig` cross path, must carry a glibc-verification step after the build, and must not pass `--host-glibc` without a matching `[[exceptions]]` entry. `PKG-006`'s existing per-platform wheel-tag match (`ci-lint release verify`) already rejects a staged wheel whose `platform_tag` doesn't match the declared platform's `manylinux_2_17_<arch>` pattern (e.g. a `manylinux_2_34_x86_64` wheel matches no declared platform and is flagged), so the tag-vs-declaration half of this floor is enforced at the artifact today; `PKG-007` adds the workflow-level guarantee that produced the artifact in the first place.

**Decision (the `rust-pypi-app` profile's packaging guarantees):** Soldr is the *only* PEP 517 backend -- `pyproject.toml`'s `build-backend = "soldr"`, a `soldr` version requirement, and maturin appearing only as Soldr's own internal dependency in `uv.lock`, never a direct build-system requirement (`PKG-004`). The command the wheel installs on `PATH` is the bundled native Rust binary, never a Python `console_scripts` shim (`PKG-003`, checked both statically against `pyproject.toml` and at the artifact by inspecting the wheel's own bytes with `zipfile` -- magic-byte platform match, no shebang, no shadowing `console_scripts` entry). Wheels are `abi3`, one per platform rather than one per CPython version. Ruff (including import sorting) plus `ruff format --check` plus Pylint run in the fast lane (`GEN-004`, policy-general.md). Proven in zackees/template-python-rust-cmd#16 (PyO3 abi3-py310, the Soldr PEP 517 backend bundling the native `template-cli` into the wheel) and zackees/ci.yml#11/#13 (`ci-lint wheel check`/`wheel installed`, `PKG-003`/`004`/`005` proofs).

**Decision (float soldr by default, zackees/ci.yml#18):** a repository tracks current soldr through `soldr>=<floor>` in `pyproject.toml`'s `[build-system].requires` and `zackees/setup-soldr@v0` with no literal `version:` input, resolving the latest release rather than freezing on one. `PKG-004` no longer requires the pin to be exact -- a floor (`>=`/`~=`/`>`) satisfies it -- and `RUST-013` flags the opposite failure mode: an exact `soldr==` pin (in `[build-system].requires`) or a literal `setup-soldr` `version:` input, either of which goes silently stale. A repository that genuinely needs an exact pin (e.g. zackees/clud's DD-020 lockstep, born from soldr#1934's unbounded-`>=` incident) records it as a `[[exceptions]]` entry (`rule = "RUST-013"`) with a reason, owner, and an automated bump path, rather than pinning silently. Protecting against a bad upstream release is soldr's own release gate's job, not every downstream consumer's.

**Decision (reconciling `SEC-004`'s SHA-pin requirement with float-by-default, zackees/ci.yml#33, closes #33):** `SEC-004` (policy-general.md) requires every third-party `uses:` -- including `zackees/setup-soldr` -- be pinned to a 40-hex commit SHA, which is the opposite direction from #18's "float `setup-soldr@v0`" default, and is not optional wherever GitHub's own `sha_pinning_required` repository setting is on: that setting rejects a floating `@v0` ref before any job runs, so zackees/soldr had to re-pin `setup-soldr` by exact SHA (soldr#3445) even though it is the fleet's own reference for floating. The fleet does not choose one rule over the other; it applies both, in order:

1. **`setup-soldr@v0` (no `version:` input) is the default** for every repository that can use it -- i.e. every repository that does *not* have `sha_pinning_required` on. This is `SEC-004`'s existing "pinned to a full commit SHA" requirement's one standing carve-out: `zackees/setup-soldr@v0` (and its `/cook`, `/cleanup` sub-actions) is the fleet's single sanctioned first-party floating ref, because its `v0` tag moves only through setup-soldr's own gated promotion (`update-v0-tag.yml`'s exact-main contract plus a FastLED/fbuild canary), not through an arbitrary maintainer push -- unlike a third-party action's floating tag, which `SEC-004` is right to reject outright. Every *other* action, first- or third-party, stays SHA-pinned; this carve-out names `zackees/setup-soldr` specifically and does not generalize.
2. **A repository with `sha_pinning_required` on (or any other repository that has decided it must pin `setup-soldr` by exact SHA) is not exempt from freshness.** It satisfies `SEC-004` by pinning to a commit SHA as required, but that SHA must not silently rot: `RUST-014` (this round, `ci_lint.rules.setup_soldr_freshness`, wired into `ci-lint audit`) flags a pinned SHA that is missing a release setup-soldr's own maintainers marked critical in its release notes (case in point: setup-soldr#539/v0.9.81 and #541/v0.9.82, which fixed Dylint caches never saving -- `RUST-004` above -- and cost kernal-api's Dylint job ~9.5 min of avoidable cold-compile on every commit until zackees/kernal-api#368 bumped the pin), or that has drifted more than 5 releases behind latest regardless of criticality (issue #33's sweep found 10 of 13 repos stale, spread across nine different refs -- unbounded drift is itself the failure mode, not only a missed critical fix).
3. **No repository is left silently stale.** Between (1) and (2), `RUST-013` (an exact pin with no exception) and `RUST-014` (a SHA pin that's gone stale) together cover every way `setup-soldr` can freeze: (1) says don't freeze without a reason, (2) says if you must freeze, the freeze must not rot. Unlike `RUST-013`, `RUST-014` is a *live* check (it queries `zackees/setup-soldr`'s own GitHub releases API, so it cannot run as a pure static precheck) and is never silenced through ci.toml's `[[exceptions]]` table -- `ci_lint.exceptions.apply_exceptions` is only ever applied to `precheck`'s static findings, not to `ci-lint audit`'s live ones (the same rule SEC-005/006/007 and GEN-006/010/011 already follow); a repository with a documented reason to stay behind records that reason in the PR that would otherwise bump the pin.

Option 2 from issue #33 (a periodic fleet-wide sweep bot opening bump PRs) remains open and is not implemented by `RUST-014` -- `RUST-014` is a per-repository live check an agent or `ci-lint audit` run surfaces, not a scheduler that files PRs on its own; issue #2 (the fleet inventory) and a scheduler are still prerequisites for that, per AGENTS.md item 1.

### npm package

- If the Rust application ships through npm, create the Linux package artifact in the quick path, install the resulting `npm pack` tarball in a clean test project, and smoke-test the exported command or module and bundled native binary where present. Check the package contents rather than relying only on `cargo test` or source-tree JavaScript tests.
- Keep Windows/macOS binary packaging, broad Node version matrices, and publication in separate validation or release workflows. Do not publish to npm from an ordinary PR.

When an app ships through both registries, test both package surfaces. A repository whose npm package is only an editor extension or wrapper should declare which published artifact is covered and which check supplies its smoke test; do not assume every `package.json` is a Rust package.
