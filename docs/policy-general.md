# General code repository CI policy

This policy applies to active code repositories under `zackees`, `FastLED`, and `TechWatchProject`. Some rules below are already enforced, mechanically, by [`ci_lint`](../ci_lint/) (this repository) against a repository that adopts `ci.toml` schema 3 -- see [docs/ci-toml.md](ci-toml.md) for the full field-by-field reference and rule catalog, and the "Status" column in [Rule and exception decisions](#rule-and-exception-decisions) below for which rules that is, per rule ID. Rules marked **candidate** describe the intended fleet contract but have no checker implementation yet; do not treat a candidate rule as already enforced anywhere.

The reference implementation of this policy is [`zackees/template-python-rust-cmd`](https://github.com/zackees/template-python-rust-cmd), built and measured round by round in [issue #6](https://github.com/zackees/ci.yml/issues/6). Its `ci.toml` is reproduced verbatim (apart from repo-specific values) as [`examples/rust-pypi-app/ci.toml`](../examples/rust-pypi-app/ci.toml).

## Required quick PR gate

- Use `.github/workflows/ci.yml` as the discoverable entry point for ordinary `pull_request` validation. It may call reusable workflows or repository scripts. Migration of an existing workflow name is a tracked change, not grounds to claim its checks are absent before inspecting them.
- Keep required jobs in this quick gate on Linux. Put necessary Windows/macOS builds, device tests, full package matrices, and long integration or end-to-end suites in separate workflows. A separate workflow may still run on PRs when its coverage is required; record whether it is a required merge check and include it in PR timing.
- Declare the repository's profile and required check names in the future central fleet inventory. Profiles describe the tests that must run; the existence of `ci.yml` alone does not satisfy coverage.
- Keep check names stable so required-check settings and timing comparisons remain meaningful. A skipped or removed required check needs explicit review.
- Reusable workflows are encouraged where they reduce duplication. Inspect both the caller and called workflow before deciding what a job actually runs.
- Track execution hosts separately from artifact targets. Linux x64 musl, Linux x64 glibc 2.17, Windows x64 GNU, and Windows x64 MSVC are distinct target cases even when a Linux runner cross-builds them. ARM64 variants are likewise distinct. The proposed target contract and release gate are detailed in [proposal.md](../proposal.md) (background: its event-selection/contract *schema* is superseded by schema 3, see the note at the top of that document; its target-model and release-lifecycle material still applies).

## The reference contract: `ci.toml` and `ci-lint`

**Decision:** a repository's CI contract lives in its own `ci.toml` (schema 3, [docs/ci-toml.md](ci-toml.md)), not in generated YAML or a second copy of routing logic. `.github/workflows/ci.yml` is the *only* PR entrypoint (`pull_request`, `push` to the default branch, `schedule`, `workflow_dispatch`); its first job calls `.github/workflows/ci-pre.yml` (never `ci-precheck.yml`, `GEN-014`) through `workflow_call`, installs nothing (`GEN-018`), and must complete in a bounded time budget (issue #6's working target is ≤ 30 s; the template's measured precheck is 5-8 s -- zackees/template-python-rust-cmd, round-3A). Inside `ci-pre.yml`, concurrency is per job: only the `cache-janitor` job is serialized, on the repo-wide non-cancelling group `cache-janitor`, and no check job takes a lock or waits on it (`GEN-015`/`GEN-016`/`GEN-017`; zackees/ci.yml#23). Every other job `needs:` the precheck job and reads its `plan.json` output; no job contains its own selection logic. This closes the drift `ci_lint` was built to catch: a second, hand-maintained routing script (e.g. a repository's own `ci_matrix.py`) that can silently diverge from what the workflow actually runs. Proven in zackees/ci.yml#10 (the strict schema-3 loader and static precheck, 34 rule IDs across 9 groups) and zackees/template-python-rust-cmd#17/#18 (the template's `ci.yml` + `ci-pre.yml`, the fast lane, and the `CI OK` gate).

**Decision:** tags are PR-title markers combined by pure set algebra: `selection = (flow base ∪ tag adds) − tag removes`. Tags have no precedence, and every platform/suite/group a repository declares automatically derives its own tag (`ci-<platform-id>`, `ci-<group>`, `ci-test-<suite>`, `no-test-<suite>`), so a tag can never drift from what it's supposed to select. A tag with a `remove` clause always makes the run `mergeable = false` -- a repository cannot silently drop required coverage by tagging it away. `CI OK` is the single required check: it aggregates every job the plan actually selected (`required_jobs`), and a `skipped` job that isn't a live-verified reuse of an already-green run counts as a failure (`TEST-001`), never a silent pass. Proven in zackees/ci.yml#15/#21 (the planner's platform-lane matrix outputs, title-edit reuse, and gate reuse verification) and zackees/template-python-rust-cmd#19 (tag-selected platform lanes cross-built on Linux and executed natively, `[ci-full]` green across 5 platforms + integration).

## Selecting full PR coverage

Use `ci-full` (or an equivalent full-matrix marker) for changes to platform
implementation code, not for business logic that calls platform code. Inspect
the changed implementation: native API/FFI handling, OS-specific branches,
platform adapters/selectors, and platform-specific runtime contracts qualify.
An unchanged platform call, a shared orchestration refactor, or moving existing
OS-specific code unchanged into a helper does not qualify. A filename such as
`session.rs`, a PTY-related feature, or a local validation gap is not evidence
of a platform implementation change.

Before adding the label, name the changed platform implementation and the
native behavior the extra lanes validate in the PR description. Use the
smallest existing tier covering the affected platforms; reserve the full
matrix for platform changes needing that coverage. Routine business logic
keeps the required quick lint, cross-target checks and representative tests.
Release/candidate validation still runs its complete required matrix.
Apply this decision at every agent entry point: repository instructions,
platform skills, planning/review/integration/landing procedures and local
validation playbooks. A tool listing available targets is an inventory, not
an instruction to check every target. Additional per-target checks exercise
only the changed platform implementations; scope commands to their platform
crates where the repository provides that boundary. Do not add a second
cross-target loop when the routine gate already supplies those checks.
Preserving remote CI means keeping required checks, not adding optional
native/full labels to business-logic PRs.

This is a selection policy for agents and reviewers; ci-lint does not infer
semantic changes from a diff or automatically enforce this distinction.

### Front-loading build-system changes (GEN-027)

In a repository whose lanes are path-scoped, the files that select the
expensive platform lanes are usually build-system files: export lists, CMake
files, `build.rs`, and test registrations. Source-only changes stay in the
cheap lane. A multi-PR series (a migration, a port, a subsystem rewrite) that
edits those files in every unit PR pays for the full platform matrix once per
PR. In obs-rust/obs-studio#2288, a long migration repeatedly touched build
files and repeatedly triggered the full matrix.

When planning such a series, batch the build-system and test-registration
changes for each subsystem into one front-loaded PR. That PR adds the
characterization tests, the stubs, and every export, CMake, `build.rs`, and
test-registration entry the series will need. The later implementation PRs
then touch only source and stay in the cheap path-scoped lane. Finish with one
batched switch-over PR if the series needs one. This cuts the series from N
full-matrix runs to about 2. Repository coverage stays the same: the
front-loaded and switch-over PRs run the full lanes their paths select, and no
required check is skipped.

This rule does not override "Selecting full PR coverage". It decides how to
split the work. It does not decide which lanes a PR selects. A PR that changes
a platform implementation still needs its native coverage, even if its
build-file edits were moved to an earlier PR. Do not reorder edits to keep a
real platform change out of the lanes that validate it. This is planning
guidance for agents and reviewers, and ci-lint does not enforce it. A possible
later ratchet would flag an implementation-labelled PR that touches shared
build files.

## Default-branch validation

**Decision (`GEN-021`, [issue #156](https://github.com/zackees/ci.yml/issues/156)):** a default-branch push run may skip a required job **only through verified reuse**, never by a blanket `if:` that excludes default-branch pushes and never by deleting the `push:` trigger, unless the repository proves live (per `GEN-010`'s live half, `ci-lint audit`) that a merge queue validates the exact merge commit -- the clause the fleet-wide removal campaign exercises beginning 2026-10-24 ([#432](https://github.com/zackees/ci.yml/issues/432); conditions in "Merge queue and the end-of-queue cache janitor" below). Verified reuse means all of:

1. **Tree identity.** The pushed commit's tree SHA equals the tree SHA of the head of the one merged pull request associated with it (`GET /repos/{r}/commits/{sha}/pulls`, bound by `merged_at`, `base.ref` = the default branch, and `merge_commit_sha` = the pushed SHA). Zero or several such PRs: no reuse.
2. **Per-job proof.** The newest decisive `pull_request` run of the named workflow on that head concluded `success`, and every job the default-branch run would execute -- a caller-supplied list that must cover the default-branch tier -- has `conclusion == success` in it (skipped, cancelled, neutral, or missing is not proof). A run in an iteration mode that skips the Linux lanes, like clud's `ci-windows`, never qualifies.
3. **Freshness.** Every proving job completed within a caller-set maximum age (default 24 h), bounding environment drift (dependency releases, runner images, time- or data-dependent tests).
4. **Fail closed.** Any API error, rate limit, missing field, or ambiguity yields "no reuse" (run the full checks), never "reuse".
5. **Visible.** When reuse happens, the run's aggregator (`CI OK` or equivalent) still reports success **with provenance** (source PR, proving run id/URL, tree SHA), so a green default-branch commit is never an unexplained skip.
6. **Cache writers are not validation.** Jobs that exist to write default-branch caches (`CACHE-003`/`[cache].write-on`) keep running on reused pushes unless the repository moves those writes to a scheduled default-branch run.
7. **Merge-queue evidence is opt-in and proves the pushed commit** ([#419](https://github.com/zackees/ci.yml/issues/419), #423/#424/#429). A merge queue merges a PR that is behind the default branch, so tree identity with the PR head fails (`tree-mismatch`) even though the queue already validated the exact commit this push introduces. With `reuse-check --queue-evidence` (opt-in, off by default), a `tree-mismatch`, `no-successful-run`, or `required-job-not-success` on the PR head falls back to the newest decisive `merge_group` run whose `head_sha` is the pushed commit itself: the same run-selection, per-job, fork and freshness rules, and the merged-PR association is still required (a direct push never reuses). No queue run keeps the PR-head reason; a red or unfinished queue run is its own refusal. The decision document's `proving_sha` names the commit the proving jobs ran on -- the PR head, or the pushed commit for queue evidence -- and `ci-lint gate --default-branch-reuse` re-verifies each proving job's `head_sha` against it (falling back to `pr_head_sha` for documents that predate it), so a queue-proven skip counts only when the proving jobs really ran on this push's commit.

A repository with no verified-reuse mechanism that skips default-branch jobs, or that documents "main is validated by the PR" without proof, is non-compliant. `pull_request` CI that tests the PR **head** (not the merge ref) does not validate the merged tree unless the tree-identity condition holds; it was the only test for 40% of zackees/clud's merges in the sampled window. The sanctioned mechanism is `ci-lint reuse-check` (GET-only, fail-closed), adopted in `--mode shadow` first and promoted to enforcement only after `ci-lint reuse-report` shows zero unexplained false reuse over at least 14 days and 100 decisive runs. Evidence: [docs/case-studies/clud-main-push-ci-burn.md](case-studies/clud-main-push-ci-burn.md) (the `main` push run was 22% of clud's CI runner time; 60% of merges were reuse-eligible; a tree-identity check would have skipped 7 flaky red `main` runs and none of the 5 real failures). Full design, rollout, and reference wiring: [docs/designs/default-branch-verified-reuse.md](designs/default-branch-verified-reuse.md).

## Status badges and per-target sweeps run on the default branch

**Decided ([#124](https://github.com/zackees/ci.yml/issues/124), `GEN-026`).** A README badge must show the default branch's state, and the full per-board/per-target matrix must not run from feature branches. Evidence (FastLED/fbuild): unfiltered `badge.svg` URLs showed whatever run GitHub picked, including branch `workflow_dispatch` sweeps and month-old cancelled runs. A cancelled run renders as **failing**. GitHub also serves cached badge images inconsistently, so badges flapped between passing and failing with no new runs, even though all 67 platform workflows were green on `main`. Separately, one branch dispatching the full per-board matrix started ~170 runs. Each run recompiled the tool, and their ~150 GB-scale cache saves evicted `main`'s caches.

1. **Badges:** every workflow badge URL carries `?branch=<default>` (e.g. `badge.svg?branch=main`). Do **not** add `event=push` when the workflow is dispatch/`workflow_call`-only; it freezes the badge on the last push-era run.
2. **Keep badges current by running on main:** per-board workflows get their main-branch runs from a path-selected dispatch on `main` (only boards affected by the change) plus a full sweep on a schedule. Scheduled sweeps skip when there are no new commits.
3. **Full matrix is opt-in on branches:** PRs run a representative subset; the full set only via a label (e.g. `ci-full`) or manual dispatch (see "Selecting full PR coverage").
4. **Compile once:** one job builds the tool and uploads it; board jobs download it (`policy-rust`).
5. **Cache saves from the default branch only** (`CACHE-003`); other refs restore from it.
6. **Storm response:** document a one-liner that cancels all queued/in-progress runs for a repo, and loop it until nothing is left, because pushes to `main` during the cancel start new runs.

Reference implementation: FastLED/fbuild#1574 (dispatch + compile-once + main-only caches) and FastLED/fbuild#1583 (badges pinned to `main`). The broader fan-out bounds proposed in [#122](https://github.com/zackees/ci.yml/issues/122) (tiered triggers, path-to-family selection, per-branch concurrency caps, a per-repo concurrent-job budget) overlap clauses 2-4 but remain an open proposal and are not adopted here.

## Merge queue and the end-of-queue cache janitor

**Decision (`GEN-022`, [issue #405](https://github.com/zackees/ci.yml/issues/405)):** every repository merges to its default branch through a GitHub merge queue. The required CI workflow triggers on `merge_group`, and the default branch's ruleset enables the queue. A direct push or a plain PR merge into the default branch is not the policy path.

**Transition and the push-revalidation removal (decided 2026-10-24, [#432](https://github.com/zackees/ci.yml/issues/432)):** adoption and removal are tracked per repository in #432. Inventory at decision time: bosn and clud are queue-live (active `main merge queue` ruleset and a `merge_group` trigger) yet still re-run validation on every default-branch push; soldr, zccache, kernal-api, running-process, reld, template-python-rust-cmd, and fbuild have queue and trigger neither. For a queue-live repository the `GEN-021` escape clause is no longer theoretical: its validation jobs may blanket-skip the default-branch push once `ci-lint audit` proves the queue live, and the push-triggered revalidation is then **removed, not deduped** -- `reuse-check` stays the sanctioned path for repositories without a live queue. The removal is gated on GEN-021 clause 6: every cache writer the push run carried must be relocated first (its own `schedule`/`workflow_dispatch` trigger, or a dedicated writer job that builds without gating), and relocation is proven from runs before the validation skip lands. Never delete a trigger whose run is still the only remote cache writer -- measured on bosn: `save-cache-remote` fires only on `refs/heads/main` inside the `rust` and `linux` jobs, and bosn has no `schedule`, so a bare removal would freeze the fleet's main-scoped cache supply.

When `[cache].budget` is declared, the merge queue run **ends with the cache janitor**. That is a job that runs `ci-lint cache janitor`, depends directly or transitively on every other job of the workflow, runs on `always()`, and holds the repo-wide `concurrency: {group: cache-janitor, cancel-in-progress: false}`. The queue serializes default-branch cache writes, so this point has exclusive access to the cache and sees everything the run just saved. The janitor does the LRU eviction itself, down to `[cache].budget`: after its per-family, stale and closed-PR passes, it evicts the least recently accessed entries until the repository total fits. It never evicts a family's newest base entry or an entry younger than the 10-minute grace window, and it warns when those alone exceed the budget. GitHub's own eviction therefore never chooses, so it can never drop a seed a required job restores (obs-rust/obs-studio#1269). `--no-enforce-budget` turns the repo-wide pass off.

## Language checks

- Python sources in the quick path run Ruff checks, including import sorting (`I` rules), `ruff format --check`, and Pylint with the repository's source paths and configuration. Remove standalone Black or isort checks only after equivalent Ruff checks pass.
- Model Python benchmark inputs, results, and reports with dataclasses internally; do not pass raw dictionaries between benchmark code. JSON and Protocol Buffers are valid wire formats. At the serialization boundary, type dictionaries with declared, concrete value types; `dict[str, Any]`, untyped `dict`, and equivalent `Any`-valued aliases are not permitted. A list of record dictionaries must be typed at least as `list[dict[str, TypedData]]`, where `TypedData` stands for a declared concrete value type or union. Convert and validate decoded wire data into dataclasses before using it, and serialize dataclasses only when crossing the boundary.
- **Records are typed dataclasses, not tuples or dictionaries (`PY-002`; owner directive 2026-10-01).** A function that returns several values, or a structure with named parts, returns a frozen `@dataclass` -- never a positional tuple such as `-> tuple[int, list[str], int]` (a policy violation) and never a `dict[str, X]` record. Homogeneous immutable sequences (`tuple[str, ...]`) are fine; dictionaries are allowed only at JSON/YAML/TOML serialization boundaries, typed with the declared wire value (`JsonValue`, `YamlValue`, `TomlValue`). **Parameters and annotated variables follow the same rule for complex types (owner directive 2026-10-02):** a nested map (`jobs: dict[str, dict[str, dict[str, YamlValue]]]`), an untyped map (`dict[str, object]`, `Mapping[str, Any]`), or a positional tuple (`list[tuple[str, str]]`) is a record and must be a dataclass. Still allowed: a scalar-valued map (an environment such as `os.environ`, a counter); an index of dataclasses (`dict[str, Entry]`, `dict[str, list[Entry]]`); and a single-level parsed document at its boundary (`dict[str, TomlValue]`). `Mapping`, `MutableMapping`, `defaultdict` and `OrderedDict` count as dicts.
- **No capture-then-wait subprocess output (`PY-003`; owner directive 2026-10-01).** Banned: `subprocess.run`/`call`/`check_call` with `capture_output=True` or `stdout=`/`stderr=`/`stdin=PIPE`, and `check_output`/`getoutput`/`getstatusoutput` -- they collect output in a pipe and read it only after the child exits, so a full pipe (~64 KiB) blocks the child and a daemon or grandchild that inherits the pipe keeps the caller waiting for an EOF that never comes. **Not banned: iterating a pipe while the child runs** (`Popen(..., stdout=PIPE)` consumed with `for line in proc.stdout:`, or an asyncio subprocess stream) -- that is streaming. **Strongly encouraged: the `running-process` package** ([zackees/running-process](https://github.com/zackees/running-process); `from running_process import RunningProcess, subprocess_run`): Rust-backed concurrent stdout/stderr capture, bounded waits, typed exits and process-tree containment, the process boundary soldr itself is built on. Standard-library-only code (like `ci_lint`) captures through temporary files (`ci_lint.proc.run_captured`) and forwards what it captured on failure; `DEVNULL` discards the evidence and some repositories ban it (soldr#3389), so it is a last resort. A genuine exception takes a same-line `# ci-lint: allow PY-003 <reason>`. `ci-lint py lint` enforces it in any repository with a ratchet baseline (`--baseline`, `--write-baseline`): existing sites may only go down, new files start at zero.
- **Function complexity is a ratchet (`RUST-018`, `PY-004`; zackees/ci.yml#229).** Every function stays under the linter's default ceiling -- clippy's `cognitive_complexity` (25) and `too_many_lines` (100), ruff's `C901` (10) -- and the functions already over it are excused one at a time, with `#[expect(clippy::<lint>, reason = "...")]` or a line-level `# noqa: C901`, never with `allow`, a raised threshold, a per-file ignore or a whole-file waiver. A suppression that no longer suppresses anything fails the lint (an unfulfilled `expect` under `-D warnings`; `RUF100` for a stale `noqa`), so the debt can only shrink. It costs nothing new: it rides the clippy and ruff runs every Rust and Python repository already has. A CRAP score (complexity × untested fraction, [unclebob/crapper](https://github.com/unclebob/crapper)) was evaluated and not adopted -- its coverage half needs an instrumented build and host test runs on every PR, and on zackees/soldr and zackees/clud complexity was only a weak predictor of fix churn. `ci-lint complexity --repo .` checks it without a `ci.toml`.
- To audit Python lint coverage beyond a repository’s normal path list, run `python3 -m ci_lint complexity --repo . --python-runtime` in an environment with Ruff installed. It supplies every tracked Python file explicitly, including discovery-excluded installer and benchmark paths, and extends the configured rule selection with `C901` and `RUF100`. This opt-in audit also checks tracked fixture Python files; configuration-only precheck does not establish runtime path coverage. A missing Ruff installation or failed invocation fails the command rather than reporting a pass.
- Test benchmark model validation and wire-format round trips so missing, mistyped, or changed fields fail clearly instead of silently breaking consumers.
- Other languages should declare their fast lint and test commands in the profile. Do not infer that an unrecognized workflow has adequate coverage.
- Apply the additional [Rust policy](policy-rust.md) when the repository builds Rust code.
- Apply the additional [C/C++ policy](policy-cpp.md) when the repository builds C or C++ code (CMake): `cpp/...` attestation gates, C/C++ lane pins, ccache/zccache cache families, and `CPP-*` rules.

## Cache policy

**Decision:** cache only reusable cross-run inputs; per-run outputs (nextest archives, wheels, perf results) are artifacts with short retention, never caches. Base layers (the full `registry`/`deps`/`compile`/`sdk`/`dylint`/`uv` families) are written only by the flows a repository declares as writers in `[cache].write-on` -- normally the default branch and nightly -- because a cache entry saved from a PR ref is unreachable by anything except a re-run of that same PR (GitHub's own documented behavior) and only wastes the repository's 10 GB budget. `CACHE-004` proves the declared families' worst-case footprint (steady state, plus one lockfile-change peak where old and new lockfile-keyed entries briefly coexist, plus the PR delta budget) fits under a declared `[cache].budget`, itself capped at GitHub's 10 GB default; a writer flow can drop the lockfile-peak term from that proof only by setting `pre-prune = true` on *every* writer flow. `CACHE-008`'s do-not-save table (issue #6 §6) and the live `CACHE-001/003/005/006/009` audit close the specific failures the fleet has already hit: a poisoned/empty cache entry that silently re-saves itself (clud's 253-byte Dylint entry, restored as "unusable payload" on 4 of 4 sampled `main` pushes), a base layer saved from a PR ref that nothing can ever restore (setup-soldr#527/#528), and a family re-enabled after being retired (zackees/zccache#1760 -- see "Local CI" below). PR-scoped saves are described in issue #6 §6 as a small, one-generation, capped **delta** over the `main` base, trimmed by the next precheck once a PR closes or merges; that delta mechanism's live behavior (whether a second push actually restores the first push's PR-scoped entry) is still an open, round-0-scoped probe as of this writing, so treat "PR deltas keep an agent's iteration loop warm" as the *design*, not yet a measured guarantee. Cache families must never hold linked test binaries, nextest archives, `incremental/`, or a whole `target/` directory (`[cache].never`; zackees/zccache#1525, soldr#2931-#2938) -- `ci.toml` schema 3 accepts this declaration, and `ci_lint` now classifies a payload's actual contents against it (`CACHE-007`; the live audit's family-must-be-declared gate in `cache save-ok` still covers the declaration side only indirectly, since a `never`-listed family is never declared in `[cache.family]` in the first place). Proven in zackees/ci.yml#20 (the cache runtime: `save-ok`, the live family audit, `trim`/`janitor`/`heal`/`preprune`, PR-delta pack/apply) and zackees/ci.yml#22 (per-job permission grants, the sanctioned `actions/cache*` wrapper, plan-driven cache saves).

**Decision (`#425`): cache drift is surfaced where eviction runs, not only on demand.** A repository that declares `[cache].budget` or family `max` values runs `ci-lint cache audit` from its scheduled/default-branch job -- or, at minimum, from the same job as its cache janitor -- so `CACHE-004` live drift (a family's measured footprint exceeding its declared model) surfaces between on-demand audits. Measured evidence: obs-rust/obs-studio's merge-queue growth carried a 1.17 GB Linux zccache against a 550 MB max, a 285 MB Windows ccache against 128 MB, and a 143 MB macOS cache against 128 MB -- invisible until someone ran the audit, while the janitor deleted nothing and would have evicted the warm queue cache first if a max-enforcing sweep had applied the stale number. Mechanically: the live `CACHE-004` detection is implemented (`cache audit`, #139), the default branch is inferred rather than guessed (#425 Problem 1), and every `cache janitor` run now reports live `CACHE-004` family drift as a warning naming the measured size **before** it plans any eviction -- drift is never itself deletable (`CACHE-004` is not in the janitor's rule set; the fix is a corrected `max`, a pre-prune, or eviction after review). The *schedule* is policy adopted per repository; a static rule requiring the scheduled call is a **candidate**, not implemented.

**Decision (`#222`): a superseded toolchain generation on the current lock is dead weight, not a current entry.** A soldr release rewrites setup-soldr's toolchain-signature digest and the cook-base `soldr` component *without touching `Cargo.lock`*, so one lock grows two full cache sets and every trailing-hash shape keeps them apart (measured: zccache#1875 held 12.41 GB live across a 0.9.25 → 0.9.27 bump, its pre-prune blind, GitHub's LRU the only eviction that ran). `CACHE-006` therefore also applies the generation rule zccache adopted (zccache#1876): a default-branch base entry created **before the generation epoch** -- the earliest default-branch `soldr-mini` save of the highest present soldr version, less 10 minutes of slack -- is superseded once a replacement of its restore family (build-cache: os/arch/suffix/lock with the mid-key digest dropped; registry: format/os/arch/lock with the toolchain tail dropped; dylint outputs: stripped digest; cook bases: explicit soldr/rustc version, any lock) exists **after** it. The janitor deletes these through `CACHE-006`; `preprune` must retire them **before** its forecast verdict, so the cleanup and the budget math see the same world. Post-epoch entries are never targets -- concurrent job shapes stay untouched -- and with no `soldr-mini` entries the check stays silent. Recorded limitation: a soldr **rollback** to a lower version re-seeds the epoch once on the way down.

### Content-aware checkout merging (upcoming policy, CACHE-028)

**Candidate ([issue #281](https://github.com/zackees/ci.yml/issues/281)):**
when reusing a verified source baseline alongside warm build caches, materialize
that baseline first and merge an authoritative staged Git checkout by content.
Leave byte-identical files with unchanged relevant metadata untouched, retaining
their actual mtimes. Changed contents must be written with fresh mtimes, including
same-size changes with equal or backdated checkout timestamps. Reordering a
build-output cache restore alone is insufficient: it supplies no source baseline.

The completed source inventory, file contents, executable bits and symlink
targets must match the requested Git tree before building or attesting. Reconcile
tracked deletions and type changes; protect `.git`, build outputs and cache stores.
A missing or invalid baseline falls back to the ordinary verified checkout.
Use an owned writable source materialization; this does not waive `GEN-013`'s
prohibition on copying onto a read-only restored output tree. Source-cache trust,
writer provenance and budget requirements continue to apply.

A checksum-based merge with timestamp copying disabled is one implementation
option. A local probe verified `rsync -rlpc --no-times` preserved identical-file
inodes and nanosecond mtimes and copied same-size/same-mtime changed contents;
`rsync -ac` instead copied fresh checkout timestamps onto identical files.
These flags alone do not implement tracked-inventory reconciliation or Git-tree
verification. Do not substitute size-only comparison, ignoring existing files,
or fabricated old timestamps for content correctness. See the
[official rsync semantics](https://download.samba.org/pub/rsync/rsync.1).

Promotion requires adversarial invalidation tests and a measured net improvement
on the unchanged complete PR workflow, including checkout/checksum overhead and
all-feature/all-target Dylint coverage. Full release validation remains required;
attestations never replace release checks. This is an upcoming contract, with no
checker enforcement or demonstrated end-to-end speedup yet.

## Secrets and publishing

**Decision:** publishing is OIDC trusted-publishing only; this fleet's `ci.toml`-driven repositories declare no repository or environment secrets (`[allow].secrets` is empty in the canonical example). The one job allowed `id-token: write` is named `publish`, lives directly in `ci.yml` (a reusable/`workflow_call` workflow cannot be the PyPI trusted publisher -- warehouse#11096), and is bound to an `environment` restricted to the default branch. A template or reference repository never actually publishes: its publish step is a **mock** that requests the real OIDC token, decodes and asserts its claims (`repository`, `ref`, `environment`, `event_name`, the full `workflow_ref`) in-process, and stops before any upload -- the raw token, its `jti`, and its signature segment are never printed, logged, or included in any `--json` output, by construction. Proven in zackees/ci.yml#24 (`ci_lint.publish_oidc`'s mock publisher, `ci_lint.settings_audit`'s live `SEC-005`/`006`/`007` secret/environment/permissions audit, and `ci_lint.release`'s staged release-candidate completeness gate, `PKG-006`).

## Local CI: bosn → act

**Decision:** a local CI loop must run the *same* `ci.yml` and be held to the *same* cache policy as the real one, not a separate, weaker local path. This is a direct response to zackees/zccache#1760: an agent speeding up its local bosn → act loop re-enabled a cache family the fleet had already retired (`solo-toolchain`, measured at 1.21 GB for a 3-26 s saving), reported the change as a win, and no local gate caught it, because the guard that would have caught it ran only in CI. `python3 -m ci_lint precheck --local` is both the template's agent Stop-hook/pre-push command *and* the first step of its `bosn act` run, so the same static checks -- including `CACHE-009` (a retired family's live entry, or `setup-soldr` used outside its one sanctioned wrapper with its mandatory inputs) -- fire locally, before act starts, not after a push. Nothing a local run does reaches GitHub: act runs never talk to the Actions cache service, and the local cache store is bosn-owned and machine-scoped. Windows and macOS lanes are reported "not covered locally," never as a false green. Proven in zackees/template-python-rust-cmd#20 (bosn → act local lanes and the agent precheck Stop/PostToolUse hooks; the zccache#1760 scenario fails locally with `CACHE-009` before act starts, and a retired key planted in the local store fails `ACT-001`'s check -- `ACT-001` itself, the local act cache-store audit against remote policy, is implemented as `ci-lint act audit --store-dir <dir>`, per [docs/ci-toml.md](ci-toml.md#ci-lint-precheck---live)).

## One local CI engine per machine (decided; enforcement pending)

**Decision (owner, 2026-10-07; implementation [zackees/bosn#544](https://github.com/zackees/bosn/issues/544), isolation and ownership [zackees/bosn#547](https://github.com/zackees/bosn/issues/547), policy record [#388](https://github.com/zackees/ci.yml/issues/388)):** Bosn-managed local CI runs in **one outer CI engine per host Docker engine**, with one authoritative act2 service accepting jobs from every Bosn client, repository and state directory. Many jobs run *inside* that engine; several outer Bosn CI engines running at once is not the target design. Scope is local Bosn CI only: it limits neither GitHub-hosted runners nor job containers inside the engine, and it does not cover unrelated Bosn setup/development containers.

- **Concurrency lives inside the engine.** Each run gets its own cgroup (memory, CPU and process limits), network, work tree, artifact path, artifact/cache ports and a run-scoped Docker proxy, and cancelling one run never ends another or the engine. The engine count stays one whatever the job concurrency; lowering a runner concurrency limit to one does **not** implement this decision (it still creates and retires an engine per run).
- **Why: efficient cache storage.** A persistent engine and one shared cache volume let image, build-tool and action state be loaded once and reused instead of hydrated into a private store per run. This is the rationale, not a measured guarantee: savings must be shown with physical allocation and warm-hit measurements, and a singleton topology does not by itself bound disk growth.
- **One cache owner, still synchronized.** One authority owns cache metadata, publication, expiry and maintenance ([zackees/bosn#508](https://github.com/zackees/bosn/issues/508)). Parallel jobs inside the engine still need safe writes; a shared volume does not make concurrent writes synchronization-free.
- **Still required:** separate workspaces and artifact namespaces, per-run cancellation and resource limits, bounded storage with automatic expiry, and visible maintenance results. Do not prescribe broad `docker system prune`-style cleanup; Bosn removes only objects it proves it owns.

**Current versus target (2026-10-10).**

| Stage | Status |
| --- | --- |
| Policy | Adopted (this section). |
| One engine shared by one daemon's concurrent runs | Shipped on Bosn `main` ([bosn#593](https://github.com/zackees/bosn/pull/593), [#598](https://github.com/zackees/bosn/pull/598), [#601](https://github.com/zackees/bosn/pull/601)), with idle retirement. |
| One engine per host Docker engine, across daemons and state directories | Merged to Bosn `main` in [bosn#606](https://github.com/zackees/bosn/pull/606): an atomic Docker-name claim (`bosn-ci-engine-claim`), slots leased inside the engine, dead-holder takeover, and a drain of legacy per-run engines. Verified on a throwaway Docker engine; see bosn#544 for the evidence. |
| act2 serve mode owning admission, isolation and the cache inside the engine | Planned (bosn#547 step 3). Until then Bosn runs act per run inside the shared engine. |
| Published release and installed-host verification | Pending: rollout is complete only once a released Bosn proves singleton behavior and effective automatic maintenance on the target host. |

**Migration.** Per-run engines are legacy. A migration drains them: an engine still running a job is left to finish (never force-killed), and only an idle one whose ownership labels are proven is removed, with its private storage, and its absence verified. Per-run engines remain only as an explicit opt-out (`[engine] shared = false`) and on hosts where the engine's socket directory cannot be shared (Docker Desktop VMs).

**Enforcement:** none in `ci_lint` today. A candidate check would flag a repository-owned local CI wrapper that starts its own act engine instead of going through Bosn's engine; it is not implemented.

## Local workflow execution uses act2 (candidate ACT-002)

**Decision ([issue #213](https://github.com/zackees/ci.yml/issues/213)):** a repository that runs GitHub Actions workflows locally -- through bosn's CI engine or a repository wrapper such as zackees/clud's `ci/act_ci.sh` -- uses **act2** ([zackees/act2](https://github.com/zackees/act2), the fleet's fork of nektos/act), not upstream act. act2 is pinned by version and sha256 digest, the way bosn pins act today (`crates/bosn-core/src/act.rs`: `ACT_VERSION`, `act_binary_digest`, and the engine/runner digests).

**One action-cache behavior, no switch.** act2 keeps only the content-addressed bare-repository action cache; the old working-tree cache and the `--use-new-action-cache` flag are removed. Callers pass no legacy cache flags (`--use-new-action-cache`, and `--action-offline-mode` if act2 drops it) and carry no compatibility toggles. Legacy cache behavior is not supported.

act2's acceptance criteria:
1. The bare-repository cache is the only cache.
2. **Resolve once.** A `uses:` ref that is a full SHA already in the cache makes no network call. Tag and branch refs are resolved at most once per run (or under a short TTL), or the caller (bosn) resolves every ref at run start and passes pinned SHAs. This removes the per-job × per-action GitHub round trips and the rate-limit exposure of bosn's `max(1, ncpu*2)` concurrent slots (zackees/bosn#358, zackees/bosn#376).
3. **Cross-process safety.** A per-repository file lock around init and fetch: in act v0.2.88 `git.PlainInit` races and go-git's shallow/packfile writes are not multi-process safe (`pkg/runner/action_cache.go`, `action_cache_offline_mode.go`). Reads by SHA need no lock.
4. **Unpack once.** Each SHA is unpacked once into an immutable, read-only directory keyed by SHA, so `GetTarArchive` does not re-walk the git tree on every file read and copy.
5. **Tests:** N concurrent jobs sharing one cache, zero network calls when warm, a run killed mid-fetch, and an unwritable cache directory.
6. **Runner parity.** act2 sets `RUNNER_ENVIRONMENT` the way GitHub does, beside the `RUNNER_OS`/`RUNNER_ARCH`/`RUNNER_TEMP`/`RUNNER_TOOL_CACHE` it already sets: `github-hosted` for a container platform (act's runner images emulate GitHub-hosted runners) and `self-hosted` for act's `-self-hosted` host mode. Upstream act sets no `RUNNER_ENVIRONMENT` at all, so every action whose default keys on it (for example `astral-sh/setup-uv`'s `enable-cache: auto`, which caches only on GitHub-hosted runners) silently behaves as if on an unknown runner, and repositories compensated with per-step overrides (zackees/clud's `enable-cache: true`). Tests: one job per platform kind asserting the value.

Evidence: the old cache failed 3 of 4 concurrent runs with `lstat /root/.cache/act/actions-cache-restore@v4/…: no such file or directory` (zackees/clud#1724), and bosn's own engine still invokes act with that cache on a machine-wide volume (`crates/bosn-service/src/ci/engine.rs`, no cache-mode flag). act's new cache does a depth-1 network fetch for every action in every job, and its "offline mode" still tries the network first. Upstream releases about monthly, and requests for more control over action fetching (e.g. nektos/act#2672) stay open.

Rollout ([#213](https://github.com/zackees/ci.yml/issues/213)):
- (a) Stopgap: bosn's engine passes the safe cache flag unconditionally until act2 ships -- the only sanctioned use of a legacy flag, removed in (c).
- (b) act2 implements criteria 1–5, with CI and release binaries.
- (c) bosn switches its pins to act2, measuring job startup before and after.
- (d) Repository wrappers (clud's `act_ci.sh`) move to act2, or better, to bosn's engine, so act is invoked in one place.
- (e) The lock and resolve-once changes go upstream to nektos/act as PRs, so act2 tracks upstream with a small patch set.

## Stock actions work out of the box under act2 (candidate ACT-003)

**Decision:** a workflow that runs on GitHub runs unchanged under bosn → act2. A repository's workflows and composite actions carry **no act-only workaround**: no `env.ACT`/`ACT`-conditional input or step, and no cache input forced on (`enable-cache: true`, `save-cache: true`) whose only purpose is the local runner. Where a stock action does not work out of the box locally, the fix lands where the difference lives -- act2 (runner parity, criterion 6 above), bosn's engine, or the action itself -- not in each repository.

**Exceptions are tracked, not silent.** A stock action that still needs a local workaround is an exception: an issue in zackees/ci.yml labelled for ACT-003, cross-referenced with zackees/act2 and zackees/bosn (and the action's own repository), naming the workaround's exact location and the change that removes it. The workaround carries a comment linking that issue. A workaround without a tracking issue is a violation once ACT-003 is enforced.

**Two signals, two jobs.** Runner parity and "is this local?" are separate questions with separate answers:

- `RUNNER_ENVIRONMENT` / `runner.environment` answers **parity**. act2 sets `github-hosted` in a job container exactly as GitHub does (criterion 6), so a stock action's GitHub-hosted defaults (for example setup-uv's `enable-cache: auto`) engage with no override. It must never be repurposed to mean "local".
- `ACT=true` (exported by act and act2 for every job) is **the local-runner signal**. A local runner has a different cache economy from GitHub: no 10 GB repository budget and no ref scoping, a slow refetch over the developer's network, and a fast local disk. An action **may and should** read `ACT` itself to tune its cache for that: save on every event, keep a larger cache, prune less, compress less (or faster). `zackees/setup-soldr`'s `save-cache: auto` does this (setup-soldr#537). Fleet-owned actions put such tuning behind `ACT` in the action, never behind a new variable or a per-repository input.

A repository's workflow reads `ACT` only where a stock action exposes the right knob but has no runner-aware default. That is an exception: it carries a comment linking its tracking issue.

Keep a planner's **remote write permission** separate from an explicit **cache disable**. A read-only PR flow must continue to prohibit remote uploads while the shared action can retain compatible local artifacts under act2. An explicit disable still disables every save, including local saves. Implement that distinction in the shared action's input contract; do not override a planner's `false` with an `ACT` expression in each repository. The `save-cache-remote` contract shipped in [setup-soldr#565](https://github.com/zackees/setup-soldr/pull/565). Its exact merged SHA passed the [full fbuild canary](https://github.com/FastLED/fbuild/actions/runs/37101793881) and was [promoted through the prescribed workflow](https://github.com/zackees/setup-soldr/actions/runs/37103685561) to `v0`. Consumers pass their planned permission to `save-cache-remote`, leave global `save-cache` at `auto` for ordinary local reuse, and retain explicit global `false` where all writes are intentionally disabled.

Runner parity includes filesystem permissions: an emulated GitHub-hosted VM must start its commands with the VM's `0022` umask. An emulated GitHub-hosted Linux VM must run shell steps and JavaScript actions as an ordinary user, with a writable HOME, workspace parent and generated workflow directories. That user must retain Docker command access to the job's intended daemon without changing a mounted socket's ownership or permissions. Explicit job containers, Docker actions and services retain their declared image/user semantics. Provisioning must preserve ownership of host-bound paths, including mounts supplied through container options; account and sudo configuration must remain on the job's private filesystem. The unchanged running-process quick lane exposed the root-user mismatch ([act2#9](https://github.com/zackees/act2/issues/9), [migration evidence](case-studies/fleet-ci-migration-baseline.md#running-process-unchanged-baseline-shared-runner-parity-failure)). Keep an explicit job container's Docker execution semantics separate. Fix a runner mismatch in act2/bosn rather than adding `umask` branches or loosening a product's private-directory contract in each repository. This is part of candidate ACT-003, not a new implemented static check.

Known exceptions:
- `zackees/setup-soldr`'s `save-cache: auto` skipped every save on a `pull_request` event. Fixed by setup-soldr#563, and the repository overrides are removed once `v0` carries it ([#216](https://github.com/zackees/ci.yml/issues/216)).
- `astral-sh/setup-uv` prunes wheels before saving, which empties a local cache. Repositories key `prune-cache` and `cache-suffix` on `ACT` ([#226](https://github.com/zackees/ci.yml/issues/226)).
- bosn's rewritten workflows leaked into job checkouts ([#219](https://github.com/zackees/ci.yml/issues/219)), act job containers had no init ([#220](https://github.com/zackees/ci.yml/issues/220)), and bosn's default engine storage was too small for a multi-job Rust workflow ([#221](https://github.com/zackees/ci.yml/issues/221)). The first two are fixed in act2 `v0.2.89-act2.1` and bosn 0.1.8. None of the three needs repository workarounds.

Enforcement is **candidate**. A static `ci_lint` check would flag `env.ACT`/`ACT` in a workflow or composite-action expression or `run:` condition, and a forced `enable-cache`/`save-cache` input, unless the line links an open ACT-003 exception issue.

Enforcement (ACT-002) is **candidate**. A later static `ci_lint` check would scan the local-CI surfaces `RUST-001`'s `ci_lint.gate_bare_tools` already reads (`ci/*` wrappers, `bosn.toml` tasks, local-gate lanes) and flag a bare `act` invocation instead of the act2 pin or bosn's engine, any legacy cache flag (`needs_review` until (c) ships), and a repository-owned act pin that names a nektos/act version or lacks a sha256 digest.

## Local gate first (GATE-001..005)

**Decision ([issue #166](https://github.com/zackees/ci.yml/issues/166)):** a pull request should pass remote CI on its first push, so the remote quick gate must be a **subset of one local command**, and remote runner time is refused to a head commit that never passed it. A repository declares that command once: `[local.gate].run` in `ci.toml`, or `[gate].run` in a repo-root `local-gate.toml` for a repository that has not adopted `ci.toml` (same table; declaring both is itself a `GATE-001` violation). Then:

1. **Remote ⊆ local (`GATE-001`, static).** Every job listed in `mirrors` (e.g. `ci.yml:lint`) runs the gate argv -- optionally with trailing lane arguments -- and nothing else. Any other `run:` line, or a `uses:` step outside the known setup actions (checkout, setup-python/node/go/uv, cache restore, rust-toolchain, setup-soldr), is a violation unless that step is named in `setup-steps` because it only prepares the environment. A remote check therefore cannot exist that the local gate does not run.
   An opt-in `[gate.replay]` declaration additionally requires source-bound Bosn/act2 execution evidence before a pass is cached or attested ([schema reference](ci-toml.md#localgate-gate-001005-007-zackeesciyml166-168-177)). Static validation binds job names, complete dependency chains (including literal local reusable calls) and executed check names to the repository workflow; runtime validation requires the clean exact source, declared event/inputs, successful jobs and unambiguous successful Main steps -- with one declared-by-source exception ([#415](https://github.com/zackees/ci.yml/issues/415)): a *conditional* step whose `if:` reads a runtime-dynamic step output of a step that runs (a pass-marker `cache-hit` lookup) is proved by exactly one Main section that either succeeded or explicitly skipped, because a marker hit skips it by design; absent, duplicated, failed or cancelled evidence still rejects. Informational literal messages are not checks; setup-step waivers do not exempt replay actions. Dynamic coverage remains `needs_review`. This additional evidence does **not** yet replace the command-style mirror mechanism: #289's Bosn adoption and remote-subset acceptance remain required, and an empty `mirrors` list still reports `needs_review`.
2. **Verify first (`GATE-002`, static).** The PR entry workflow's `verify` job runs `ci-lint local-gate verify`, has no job-level `if:`, and every other job in that workflow transitively `needs:` it (except jobs in `verify-exempt`, e.g. `ci-pre`). An unattested push costs one small job, not a fan-out.
3. **Attested head (`GATE-003`, runtime).** `ci-lint local-gate run` requires a clean tracked tree, runs the gate, refuses if the gate rewrote a tracked file or moved HEAD, and on success amends HEAD's message with `Local-Gate: v1 tree=<tree sha> secs=<n>`. The trailer is bound to the commit's *tree*: any content amend or rebase makes it `stale`; a message-only amend keeps it valid. `verify` fails the PR run when the head is `missing` or `stale`; the pre-push hook (`local-gate install-hook`, body `local-gate check-push`) refuses the same push before it leaves the machine.
   A local workflow replay (`ACT=true`, the local-runner signal above) runs
   checks to create that proof. Its `verify` command reports `local-replay`
   without requiring an existing trailer, sets `attested=false`, and never
   trusts a prior stamp: every declared per-job skip output is false.
   A successful verifier is not execution proof; `local-gate run` still
   requires the completed gate before writing a lane record or trailer.
   Hosted verification and `check-push` retain their enforcement.
4. **Measured (`GATE-004`, live).** `ci-lint local-gate first-pass` reports, for PRs merged in a window (paginated; `--limit N` keeps the newest N and the total is always printed; `--workflow` scopes to PRs with a run of that file), whether exactly one head SHA got a run that went green on attempt 1 with no failed run -- `needs_review` below 80% over at least 5 merged PRs.

The command also reports a separate earliest-head CI outcome for each scanned PR: pass, fail, or unknown, from its earliest observed workflow-run cohort. Same-head timestamp ties stay together; later duplicate triggers and review revisions do not change that initial outcome. A green review revision can miss the single-head GATE-004 criterion without any CI failure. Completed attempt-one failures, timeouts and startup failures establish a failed initial cohort; missing/incomplete evidence, initial cancellation and overwritten first-attempt history remain unknown. This companion includes PRs without workflow runs as unknown, prints both the known-outcome pass rate and evidence coverage, and never changes GATE-004's target, verdict or historical denominator. It covers only the selected workflow, not every workflow or native lane in a repository; an earlier head with no recorded workflow run cannot be reconstructed from this evidence.

On a repository that opts into `GATE-008` ([below](#attested-skip-of-the-remote-quick-gate-gate-008)), an attested in-policy PR head skips the mirrored jobs. The default-branch push and the audit sample still run them, so remote ⊆ local is still checked continuously, after merge rather than before it.
5. **Isolated, for self-hosted tools (`GATE-005`, static; [issue #168](https://github.com/zackees/ci.yml/issues/168)).** A repository that builds a tool which is also live infrastructure on the developer's own host (soldr, zccache, clud, bosn) must never run its test suite on that host: its tests start the tool's daemons and touch its state roots, and on 2026-10-01 one leaked soldr fixture claimed the real `~/.soldr` root and wedged every soldr build on the machine, other agent sessions included ([zackees/soldr#3516](https://github.com/zackees/soldr/issues/3516)). Such a repository declares `[gate.isolation]` (`marker`, `runner`, `guard`). The `guard` -- a file every test process passes through -- refuses to start unless `CI=true` (GitHub runners, act) or the `marker` is set; the isolated `runner` (today `bosn run --task <task>`, and `bosn` → `act` once act owns its Docker isolation) sets the marker; and the local gate runs the suite through that runner. `ci-lint` proves all three are wired; a known self-hosted tool repository without the declaration is `needs_review`. The guard itself is the runtime enforcement: a bare host test run refuses with the isolated command to run instead.
6. **Proven isolation (`GATE-009`, [#196](https://github.com/zackees/ci.yml/issues/196)).** An attestation is only as good as the tree the isolated runner actually saw. With `[gate.isolation] proves-tree = true`, the gate writes a fresh random nonce to `<worktree>/.gate-nonce` (gitignored), the runner's entry script prints `gate-nonce: <contents>` from its mounted `/repo` first, and the gate fails the lane unless it sees its own nonce. A container bound to another checkout then fails loudly instead of producing a false `Local-Gate:`/`Ci-Attestation:` stamp. The blame is evidence-bound ([#414](https://github.com/zackees/ci.yml/issues/414)): only a *different* echoed nonce indicts another worktree's container; a runner that echoed no nonce at all (bosn setup died before the task started — the soldr 2026-10-22 case) reports its own failure and exit code with a rerun suggestion instead, and must never advise destroying a peer session's container. **With bosn's CI engine** (`runner = ["bosn", "ci", "run"]`, the only sanctioned runner where a repository forbids direct bosn tasks, as zackees/clud does), the nonce cannot survive bosn ci's `.gitignore`-honouring snapshot. The proof is instead bosn's run record: the gate must require `workspace` == its worktree, `sha` == HEAD and `dirty` == null. ci-lint checks that the gate script reads all three, and act's `CI=true` stands in for the marker.

The trailer is an **honesty contract, not a cryptographic proof**: anyone can type it. It stays honest because the mirrored remote jobs rerun the identical command (`GATE-001`), so a forged or stale attestation becomes a visible "attested but red remotely" PR in `first-pass`, never a silent pass. Accepted without a trailer of its own: a merge commit whose first parent is attested (GitHub's "Update branch"; the remote run covers the merge), PRs from `exempt-authors` (default `dependabot[bot]`, `renovate[bot]`, `github-actions[bot]`, which get the full remote run), and non-`pull_request` events (a default-branch push is the merge of an already-verified PR). Native-only lanes (arm64 Linux, macOS, Windows target runs) are **not** part of the local gate: they stay remote-only and are excluded from the first-pass target's failure classes when the failure is a genuine platform bug or runner flake, never mirrored as if a Linux workstation covered them. Roll out with `mode = "shadow"` (verify reports, does not fail) and promote to `"enforce"` once `first-pass` shows attested heads are the norm. A repository with no workflows (this one) declares only `run`; the pre-push hook is its whole enforcement.

Evidence: soldr's 2026-09-30 22:00 → 2026-10-01 19:00 UTC window had a **43% first-push pass rate (3 of 7 merged PRs)**, and most misses were Python lint/guard-test failures a seconds-long local run would have caught -- [docs/case-studies/soldr-first-pass.md](case-studies/soldr-first-pass.md).

## Where checks run locally: host, bosn, bosn → act (candidate GATE-006)

**Decision ([issue #172](https://github.com/zackees/ci.yml/issues/172)):** the local gate places each class of check where it is both safe and faithful to the remote job.

| Check class | Local placement | Why |
| --- | --- | --- |
| Lint, format, static guards, type checks, Clippy/Dylint, dependency policy: the tool used *as a tool* | **host**, no container | Reads the tree and writes only build output; the host's warm caches make it the fastest place. |
| Tests that start daemons, brokers, or servers, or touch a tool's state roots; any test of a self-hosted tool (GATE-005) | **bosn container** (`bosn run --task <t>`) | A host run can damage live infrastructure ([soldr#3516](https://github.com/zackees/soldr/issues/3516)) and is not hermetic (12 host-only failures). |
| The remote workflow job itself | **bosn → act**, when measured parity or speed justifies it | act replays the *workflow* (same steps and env). Today `bosn act plan` resolves the job DAG but cannot execute ([zackees/bosn#302](https://github.com/zackees/bosn/issues/302)). |

**The isolated runner must reproduce the remote job, not a dev loop.** Every divergence found in the soldr pilot was an environment difference, not a code bug:
- `cargo test` vs CI's nextest: a shared-process panic poisoned an env lock and failed 6 unrelated tests;
- the image's dev-loop `CARGO_PROFILE_*` overrides and `CARGO_BUILD_JOBS=2`;
- bosn's `sh -lc` dropping the image's `ENV PATH`: 59 "rustup not found" failures;
- bosn reaping a task on an output burst ([zackees/bosn#317](https://github.com/zackees/bosn/pull/317)).

The isolated step runs exactly the remote job's commands, under the remote job's profiles and job caps. A gate lane must be **no stricter than CI** either: a broader local check that `main` cannot pass (soldr's full `cargo deny check` vs CI's `deny check bans`) attests nothing.

**Containers must not write into the host checkout** beyond build output. Each of these happened in this pilot:
- a container-created root-owned `.venv` broke every host `uv run` ([soldr#3519](https://github.com/zackees/soldr/issues/3519));
- an in-place cargo-chef skeleton, killed mid-cook, truncated real sources ([soldr#3518](https://github.com/zackees/soldr/issues/3518)).

Measured on a 16-core host (soldr):
- lint lane: **62 s** on the host, vs the remote `Lint` job's 153–163 s;
- host `rust` lane (CI's fmt/lint-ci/Clippy/Dylint/deny-bans/audit/machete commands): 181 s cold;
- bosn tests lane (CI's nextest + doctest stages, 3,559 tests): 296 s after an image rebuild, ~106 s warm;
- remote `Linux x64` (`ci-test`, warm cache): 504–555 s.

## Attested skip of the remote quick gate (GATE-008)

**Decision ([issue #190](https://github.com/zackees/ci.yml/issues/190), design and evidence [docs/designs/pr-critical-path.md](designs/pr-critical-path.md), ledger [pr-critical-path-ledger.json](designs/pr-critical-path-ledger.json)):** on a repository that opts in, a PR head carrying a valid local-gate attestation **skips** its remote quick-gate jobs. Those jobs would rerun exactly what the gate already ran (GATE-001), so on an attested head they add latency, not evidence. On soldr that latency was a median of 914 s, for ~78% of PRs.

1. **Opt in from the base.** `[gate.trust]` (`mode`, `skip`, `covered-by`, `surfaces`, `full-labels`, `audit-rate`; [ci-toml.md](ci-toml.md)) is read from the PR's **base** commit. A PR cannot enable trust, drop a lane, or narrow a surface and benefit in the same PR.
2. **Fail closed.** `ci-lint local-gate verify --trust` sets `trusted=true` only when **all** of these hold:
   - the event is a pull request;
   - no full label (`ci-full`) is set;
   - the PR is not a fork;
   - the author is OWNER, MEMBER or COLLABORATOR;
   - the head is attested for its **exact** tree (an attested first parent is not enough);
   - the trailer covers every base-declared lane;
   - no path in the merge-base diff matches a surface: the declaration, files named in the gate's or a lane's argv, their statically resolvable tracked Python imports (transitively, from the base revision), the skip and verify workflows, the local reusable workflows and actions they reference, and the declared `surfaces`; dynamic imports require explicit `surfaces`;
   - the head is not in the 1-in-N audit sample (default 10, keyed by head SHA).

   Every other case outputs a reason code, and the jobs run as before.
3. **Skip jobs are declared and wired.** Each `skip` job's job-level `if:` consumes `needs.<verify>.outputs.trusted`. A skip job that is not a GATE-001 mirror names the lanes that cover it (`covered-by`), and the scripts only it runs are listed as surfaces.
4. **The default-branch push always runs for real.** It is the post-merge catch for merge skew or a dishonest trailer, and the reason the static check fails a skip workflow with no push trigger. A reusable (`on: workflow_call`) workflow counts as push-triggered when a push-triggered workflow calls it. GEN-021 reuse already refuses a PR run whose required job was skipped. The release candidate's exact-SHA full run stays the final gate.
5. **Measure.** The audit sample runs the jobs on 1 in N attested heads. A remote failure on an attested head (audit or `main`) is a finding: switch the repository to `mode = "shadow"` until it is explained.

## Per-gate attestations (GATE-010)

**Decision ([issue #198](https://github.com/zackees/ci.yml/issues/198); reference [ci-attestations.md](ci-attestations.md)):** local evidence travels in the commit message, one compact JSON `Ci-Attestation:` trailer per gate, and CI skips exactly the remote jobs whose gates are all attested.

1. **Definition.** A repository declares its gates in `ci-attestations.yml` (restricted YAML, comments allowed). Gate paths follow `<ecosystem>/<platform>/<check>`, e.g. `rust/x86_64-unknown-linux-gnu/test` or `rust/all/clippy`. Each gate names the lane that proves it, and `jobs:` maps each remote job to the gates it runs. CI reads the definition from the PR **base**, and the file is an automatic GATE-008 surface.
2. **An entry must name a declared gate; omission means not run.** An undeclared, malformed, duplicate, re-stamped, rebased or content-changed entry is invalid and is never counted.
3. **Per-job skip.** The verify job outputs `skip_<job>` for each GATE-008 skip job. It is `true` only when the head passes GATE-008's head-level policy **and** every gate the job lists has a valid attestation.
4. **Stamp.** `sha256(tree, parents, canonical JSON)`: tamper-evident, bound to content and position, and not a signature.
5. **Host-optional lanes.** A lane declared `optional = true` (for example a local Windows VM) may report "not applicable on this host" with exit 75. It is never cached and never attested, so its gates simply run in CI. GATE-008 accepts its `n/a` provenance only when the base declares the lane optional.
6. **Push and release.** Push events never skip. **Release always ignores attestations:** every gate runs remotely on the candidate's exact SHA.
7. **Lane fidelity (`GATE-011`, [#202](https://github.com/zackees/ci.yml/issues/202)).** A gate declares how its lane reproduces the platform: `native`, `vm` or `emulation`. Pilot evidence: Wine passed 95% of soldr's Windows tests, but failed the named-pipe, ACL and junction suites. Darling wedged on signals, daemons and `fork`. A warm Windows VM passed 160/160. So an emulation lane can never prove `.../test`; it attests a scoped check such as `.../unit`.
8. **Caching.** Valid attestations may be saved as tiny side cache entries. Cache keys carry the human-readable, ancestor-defining label `m<n>-<sha10>` (main) or `m<b>-c<k>-<sha10>-pr-<N>` (the PR tag is the fleet's existing `PR_CACHE_TAG` suffix), and `ci-lint attest resolve` hydrates the nearest attested ancestor.

## Remote-only checks never gate a PR (GATE-012)

**Decision ([issue #206](https://github.com/zackees/ci.yml/issues/206); owner directive 2026-10-02):** a check that cannot run under bosn → act never gates, delays, or second-guesses an ordinary pull request. Local gate first works only if every check that can block a PR is one a developer can reproduce locally. A check that no local run can produce can't be attested, can't be debugged, and adds latency without adding evidence.

1. **Suppress by default.** A remote-only check with no merge value is turned off. **CodeRabbit is suppressed fleet-wide.** Every repository checks in a repo-root `.coderabbit.yaml` that sets `reviews.auto_review.enabled: false` and `reviews.commit_status: false`, and leaves `reviews.request_changes_workflow` and `reviews.fail_commit_status` off. An on-demand `@coderabbitai review` stays available as advisory review. Uninstalling the app is an equivalent, stronger option, but the file must still be checked in, because the file is the declaration `ci_lint` can see.
2. **Confine what must exist.** A remote-only step the repository genuinely needs may run only on `push` to the default branch, tags, `release`, `schedule`, or `workflow_dispatch`, or on a PR only behind an opt-in label such as `ci-full`. That covers publishing, Pages deploys, provenance attestation, and code-scanning upload. Such a step never runs unconditionally on `pull_request`/`merge_group`. The release candidate's exact-SHA full run remains the final gate.
3. **Never required.** A remote-only check is never a required status check on the default branch, whether through classic branch protection or a ruleset. That covers any check named by a GitHub App (`CodeRabbit`, Codecov, SonarCloud, DeepSource, Snyk, GitGuardian, Dependabot, CodeQL/code scanning) and any required check bound to an app other than GitHub Actions.
4. **Zero wait.** No tooling may wait on, poll for, or require a check that cannot run under bosn → act. That applies to merge watchers, landers, verify jobs, wait-on-check actions, and `gh pr checks --watch` loops. A suppressed or absent CodeRabbit status means **zero wait, not a grace period**. Its absence is the normal state, and a local bosn → act run never stalls on it. (Motivating case: zackees/clud's `pr_merge_watch.py` waited 120 s for an absent CodeRabbit status, and up to 600 s after CI was green.)
5. **Declare act-impossible jobs; a local run reports them and never fails on them.** Some workflow jobs cannot run under act whatever their `if:` says, because they ask GitHub about the run itself: under act, `github.run_id` is a local ID, and the Actions API answers 404. Examples are a queue-timing report and a full-coverage aggregator that reads its sibling jobs' conclusions. No registry can see this, so the job declares it with a job-level `env:` entry, `CI_REMOTE_ONLY: <reason>`, and the value is the reason.
   - On GitHub the entry is an unused variable. The job, its check name, and any required check built on it behave exactly as before.
   - A local runner treats a declared job, or one using a registered act-impossible action or `id-token: write` (the table below), as remote-only. bosn ci is the reference implementation (zackees/bosn#400). It keeps the job's `if:`, `needs:`, runner and matrix, so the job is skipped exactly when GitHub would skip it and its dependents still run. It replaces only the job's steps, and reports the job `remote_only` with its reason. A remote-only job is never a local failure and never a local coverage gap.
   - Mark jobs this way. Do not use `if: ${{ !env.ACT }}` or `github.actor != 'nektos/act'` guards: those encode one engine's environment in every workflow, hide the reason, and skip the job's dependents.
   - **Run introspection** is the one kind of remote-only job that may run on every PR, and be required, without breaking item 2 or 3: a job that only reads GitHub's record of the same run. It adds no evidence beyond the jobs it reads, and a local run executes those jobs itself, so the local run's own verdict stands in for it. Anything else a job declares remote-only stays confined by item 2.

**What act cannot run.** act runs workflow jobs in Linux containers with no GitHub backend, so it cannot run any of the following:

| Class | Examples |
| --- | --- |
| GitHub Apps (vendor-side, webhook-triggered) | CodeRabbit (status `CodeRabbit`, bot `coderabbitai[bot]`), Dependabot, Codecov/SonarCloud/DeepSource/Snyk/GitGuardian apps |
| GitHub-side services | `github/codeql-action/*`, `actions/dependency-review-action`, `actions/deploy-pages`, `actions/configure-pages` with `static_site_generator`/`generator_config_file`, `dependabot/fetch-metadata` |
| OIDC / sigstore | `permissions: id-token: write`, `actions/attest-build-provenance`, `actions/attest`, `actions/attest-sbom`, `pypa/gh-action-pypi-publish` |
| Hosted services that need tokens | `codecov/codecov-action`, `coverallsapp/github-action`, SonarCloud/SonarQube scan actions |
| Run introspection (GitHub's record of the same run) | `github.run_id` passed to the Actions API: a queue-timing report, a full-coverage aggregator. Declared with `CI_REMOTE_ONLY` (item 5) |
| Non-Linux hosted runners | `runs-on: macos-*`/`windows-*`: already governed by `GEN-002` (kept out of `ci.yml`) and the `GATE-011` candidate; GATE-012 adds nothing there |

**Stubbed locally, not remote-only.** A plain `actions/configure-pages` only reads the site's Pages metadata. A Pages *build* job uses it, then builds, validates and uploads the site with `actions/upload-pages-artifact`, all of which is local work. A local runner therefore serves configure-pages with a stub that sets its outputs (`base_url`, `origin`, `host`, `base_path`) for the repository's `https://<owner>.github.io/<repo>` site. `upload-pages-artifact` runs against act's artifact server, so the build job runs locally and is local evidence. Only the deploy (`actions/deploy-pages`) stays confined. bosn ci is the reference implementation (`remote_only::classify`, `LOCAL_STUBS`). With `static_site_generator` or `generator_config_file`, configure-pages edits the generator's config from the live site, so it stays in the table above.

The list is open. When a newly adopted action can't run under act, add it to this table and to `ci_lint.remote_only.REMOTE_ONLY_ACTIONS`/`APP_CHECK_NAMES` in the same change.

**Enforcement.** Static checks run in `ci-lint remote-only`, and are also part of `precheck` and `local-gate lint`:
- **`.coderabbit.yaml` (or `.yml`).** Missing, or leaving any of the four settings above on, is a violation; an unparseable file is `needs_review`.
- **Workflow jobs.** This applies to a `pull_request`/`pull_request_target`/`merge_group` workflow, and to a local reusable workflow its jobs call. A job that uses a registered act-impossible action, or that requests `id-token: write`:
  - is a violation when unconditional;
  - passes when a job- or step-level `if:` confines it to non-PR events or an opt-in label;
  - is `needs_review` when the `if:` is unrecognized, such as a data-dependent step output.
- **Waits.** This covers workflow steps, composite-action steps, and `ci/` scripts. A wait-on-check action naming an app check, or a `run:`/script that names one alongside a polling signal (`gh pr checks`, `--watch`, the statuses/check-runs API, `sleep`), is a violation. Only a line that names one as a check counts: it must also mention checks, statuses, check runs/suites, contexts, `required`, `conclusion`, waiting, or polling. A bare mention (a log group, a tool-cache path being cleaned, a shell comment) is not a check name. Naming one as a check without a polling signal is `needs_review`. A same-line `# ci-lint: allow GATE-012 <reason>` excuses one line.

The live check runs in `ci-lint audit` and reuses the branch-protection and rulesets payloads that `GEN-006`/`GEN-011` already fetch. A required check that names an app check, or is bound to a non-Actions `app_id`/`integration_id`, is a violation.

## Re-running the local gate: lane result cache (GATE-007)

**Decision ([issue #177](https://github.com/zackees/ci.yml/issues/177), piloted in [soldr#3529](https://github.com/zackees/soldr/pull/3529)):** a local gate lane may be skipped only when **its inputs are byte-identical to a passing run of the same lane**, and every skip is recorded in the attestation.

1. **Declare lanes** as `[gate.lanes.<id>]` (`run`, `exclude`, `keep`, `tools`, `env`, `max-age-hours`, `weight`, `group`; [ci-toml.md](ci-toml.md)). Each lane is the gate command plus arguments. Cache hits are resolved first. `light` lanes then run concurrently alongside the `heavy` chains. Heavy lanes form one chain per `group` (default: one shared group); each chain runs one lane at a time in declared order and stops at its own first failure, and different groups' chains run concurrently (#399). Put heavy lanes in separate groups only when they share no build directory, cache lock or other exclusive resource -- e.g. a test suite in an isolated container (its own target dir) beside host compiles. Every lane that passed is recorded, even when another failed, as long as the tree is untouched, so fixing the failing lane does not rerun the others.
2. **Key** = sha256 over the lane's argv, the `--version` of its declared tools, its declared env values, and `(path, blob sha)` of its input set, read from `git ls-tree`. Since [#401](https://github.com/zackees/ci.yml/issues/401) (`KEY_VERSION gate-007/v2`) the `ci.toml` contribution is **semantic** for a lane whose argv/tools do not invoke ci-lint: sha256 of the parsed document minus its top-level `linter` pin (sorted-key JSON). A pin-only bump -- the one canonical pin in consumers -- then invalidates only lanes that actually run ci-lint, instead of every lane on the machine (soldr#3556 measured ~24 min of heavy-lane reruns per bump, most of it for a pin only the guards lane consumes). Any *other* `ci.toml` field change still moves every lane, declarations remain mandatory inputs (the exclusion rule is untouched), and a lane that reaches ci-lint outside the detected argv shapes is the heuristic's known residual.
3. **Input set = the commit tree minus exclusions, never an include list.** A forgotten exclusion costs speed; a forgotten include silently skips required work. soldr's old include-list path scope did exactly that: it never listed `src/`, though the Rust build embeds `src/soldr/_bundle_bins.py`. These are always inputs, whatever the globs say:
   - the gate declaration;
   - every repository file named in a lane's argv;
   - the lockfiles and toolchain pins of the ecosystems the lane's tools use (unrecognized tools keep every pin).
4. **Only passes are cached**, in `<git common dir>/ci-lint/lane-cache/`. That location is shared by every worktree of a clone and never pushed. Entries expire after 24 h by default; `--no-cache` bypasses the cache.
5. **Provenance:** the trailer gains `lanes=<id>:run|<id>:reused@<key12>,...`.
6. **Local only:** CI's mirrored jobs always run (GATE-001).

**One full run can seed multiple lane passes** when a repository declares `[gate.full-run]` (`lane-passes-v1`). This preserves a full runner's cold parallelism: the gate command writes a tree-bound receipt naming every required lane only after validating each actual job result. The checker accepts it only after a successful command and unchanged tree; missing, partial or mismatched receipts cache nothing. Optional host lanes must be explicitly passed or named as not applicable in the receipt; a not-applicable result is never cached or attested and cannot excuse a required lane. With only one cache miss, the named lane runs directly. See [ci-toml.md](ci-toml.md) for the receipt format. The gate command owns the honesty of its job claims, just as it owns its own successful exit status.

**Split lanes along input boundaries, not by tool.** Replaying 150 soldr commits (`ci-lint local-gate lanes --simulate 150`), the three tool-shaped lanes (lint / rust / tests) were reusable only 0-3% of the time. Every commit touched `crates/` (which lint guards scan) or `.github/` (which `soldr lint ci` reads). Five input-shaped lanes reach:
- py-static: Python linters, 48%;
- rust: fmt/Clippy/Dylint, 33%;
- tests: nextest + doctests in bosn, 29%.

Two lanes that read everything stay cheap or unexcludable: guards (repository scanners and the Python tests) and ci-lint (`soldr lint ci` plus dependency policy).

**Some lanes legitimately read everything.** An audit of soldr's guards lane showed its Python tests read dozens of `docs/*.md` files: doc-contract tests for release checklists, zccache guardrails and path policy. So a docs-only change rightly reruns them, and excluding `docs/**` would have been an unsafe skip. Finer reuse there needs per-test selection, not a broader exclusion.

**Prove exclusions with a trace.** `ci-lint local-gate lanes --audit <lane>` runs the lane under `strace` (open/exec and the stat family, which catches cargo's dep-info freshness checks). It fails if the lane touches a tracked file its exclusions drop. On soldr it caught `pyproject.toml` excluded from the rust lane, though soldr reads `[tool.soldr]` from it. A grep over the code had suggested `**/*.py`, `**/*.md` and `tests/**` were safe Rust exclusions; the code actually embeds files of each kind. The audit cannot see reads by daemons or containers outside the traced process tree, so container lanes rely on compile dep-info and review.

**Measured on soldr** (16-core host; bosn tests lane):

| Scenario | Time |
| --- | --- |
| first run | 748 s |
| docs-only change | **76 s** |
| Python/CI-script change, ~37% of soldr commits | **104 s** |
| Rust change | 498 s |
| revert to an already-passed tree | **0.7 s** |

Without the cache, a warm full run takes ~525 s. The first run's tests lane was cold because bosn scopes volumes per workspace path; sharing them across worktrees and ancestor commits is [zackees/bosn#327](https://github.com/zackees/bosn/issues/327).

## Cache compression tiers (candidate CACHE-023)

**Decision ([issue #173](https://github.com/zackees/ci.yml/issues/173)):** compression level is a property of the cache *tier*, chosen from measurement, not hard-coded per step.

Experiment: soldr's real `target/x86_64-unknown-linux-gnu/debug/deps` (1.83 GB tar), zstd, on a loaded 16-core host. Absolute times are approximate; the ratios are exact.

| zstd level | ratio | compress, 4 threads (hosted runner) | compress, 16 threads (local) | decompress |
| --- | --- | --- | --- | --- |
| 1 | 4.27× | 1.1 s | 0.9 s | 1.4 s |
| 3 | 4.69× | 1.9 s | 1.4 s | 1.5 s |
| 6 | 5.05× | 4.6 s | 3.4 s | 1.4 s |
| 9 | 5.25× | 8.5 s | 8.3 s | 1.4 s |
| 15 | 5.44× | 48.8 s | 33.5 s | 1.3 s |
| 19 | 6.09× | 191.6 s | 124.1 s | 1.8 s |
| none (tar) | 1.00× | — | — | 1.5 s (extract) |

What the data says:
1. **Restore cost does not depend on the level.** Decompress is 1.3–2.0 s at every level, the same as extracting an uncompressed tar. "Low compression for fast local iteration" only ever saves *save* time.
2. **Local tier (bosn volumes, act's local cache server):** zstd 1–3. It is 4.3–4.7× smaller than raw for ≤ 2 s per save, and leaving it uncompressed restores no faster. Local caches never count against the remote budget and never reach GitHub.
3. **Remote tier (GitHub Actions, 10 GB per repository, `CACHE-004`):** compression buys entries.
   - **Default-branch writer families** saved at most once per merge: zstd 9 (5.25×, about 8 s).
   - **Long-lived, rarely rewritten artifacts:** zstd 19 (6.09×, about 30% more cache per GB than level 3). soldr's cook artifacts already use `COOK_ZSTD_LEVEL = 19`. The ~2–3 min save must stay off the PR critical path.
   - **PR-scoped delta saves:** zstd 3, because they are written on the critical path and short-lived.
4. **The knobs today are compile-time constants:** soldr's `DEFAULT_ZSTD_LEVEL = 3` (cache save/load, mirrored by setup-soldr) and `COOK_ZSTD_LEVEL = 19`. Making the save level tier-selectable is the implementation follow-up.

## GitHub API budget: one controlled query mechanism per machine (GHAPI-001)

**Decision ([issue #224](https://github.com/zackees/ci.yml/issues/224)):** CI-supporting tooling on a machine reads GitHub state through one controlled query mechanism that keeps a durable local cache of everything already fetched.

**Re-querying is allowed** as long as it is **incremental**: each query is tightly bounded by what the cache already holds, so it asks GitHub only for content newer than the cache's high-water mark. Re-reading content already held is what this rule forbids.

**The primary challenge is the cache, not the polling interval.** Old content must be stored durably and indexed by resource and time, so that every follow-up query can carry a tight timestamp bound (or an equivalent cursor) and fetch only incremental new information.

**Why.** The REST budget is **5,000 requests per hour per user token**, shared by everything that machine runs under that identity: agents and their subagents, merge watchers, landers, release pollers, cache audits, and the human's own `gh` commands. Nothing coordinates them.

In one FastLED/fbuild session (2026-10-02), an orchestrating agent and two or three subagents exhausted it **twice in about two hours**, using `pr_merge_watch.py` on a 20 s interval, `gh run view` monitors on 113-job release matrices, and `gh pr checks` reads. Then every tool on the machine failed at once, including interactive commands. The waste came from unbounded re-reads: each poll fetched a run's full job list, a PR's full check set or a full comment thread again, although nearly all of it had not changed since the previous poll and was already held by another process on the same machine.

**Requirements.**
1. **One broker per (host, GitHub identity).** Agents, skills, watchers, landers and `ci/` scripts ask the broker for PR, run, job, check and comment state. They never query the API themselves.
2. **A durable cache of old content, indexed by time.** The broker persists every fetched object with its `updated_at`/`created_at` (or `completed_at` for runs and jobs). It survives process and agent restarts and is shared by every caller on the machine. Terminal objects never need to be fetched again: a completed run or job with its conclusion, a merged or closed PR, a commit's check runs once all are complete, and posted review comments (until edited).
3. **Incremental re-queries are allowed and expected.** A re-query is bounded by the cache's per-resource high-water mark, so the server returns only what changed after it. Examples:
   - `since=` on issue and PR comment and review-comment listings;
   - `created=>=<ts>` / `updated` filters on `actions/runs`;
   - `per_page` with descending order, where pagination stops at the first already-cached item;
   - `If-Modified-Since: <cached Last-Modified>` and `If-None-Match: <cached ETag>`, where a `304 Not Modified` returns no body and does not count against the primary rate limit.

   An unbounded re-fetch of a collection the cache already holds is the violation, not the re-query itself.
4. **Tight bounds.** The high-water mark is the newest `updated_at` (or `created_at`) the cache has *seen* for that resource, not wall-clock "now" minus a margin. Clock skew is covered by a small overlap window whose duplicates are de-duplicated by object id, never by widening the bound.
5. **Single-flight.** Concurrent callers asking for the same resource share one in-flight incremental query. Ten watchers on one release run cost one bounded query per refresh, not ten full fetches.
6. **Budget with a reserve.** The broker records `X-RateLimit-Remaining` and `X-RateLimit-Reset` from every response. It keeps a floor, initially 10% of the limit, for interactive and human use. Below the floor, background reads wait for the reset instead of spending the reserve. This never weakens a gate: under GEN-021/GATE-008, a deferred or failed read still means "no reuse", not "reuse".
7. **Accounting.** The broker keeps a per-caller ledger (tool, repository, endpoint, bounded/unbounded, cache hit / 304 / incremental / full), so a runaway or unbounded poller can be named from evidence.
8. **Push before poll.** A waiter subscribes to the broker's cached state for a resource, and the broker decides when to run the next incremental query. A waiter that needs only a terminal state is woken once, when that state lands in the cache.

**Scope.** This governs machine-local tooling: agents, local gates, bosn → act runs and release automation driven from a developer machine. Hosted Actions jobs authenticate with the per-repository `GITHUB_TOKEN`, which has its own budget. They are in scope only where they run a query loop, which GATE-012's zero-wait rule already restricts.

**Status.** The static signal is enforced by ci-lint (`precheck` group 20, `ci_lint.rules.ghapi_reread`). The broker itself is not implemented yet; its design is [docs/designs/ghapi-broker.md](designs/ghapi-broker.md) (implementation: zackees/clud#1743), and the broker-bypass and machine-shared-cache clauses stay candidate until it ships.

**Static signal.** ci-lint scans every workflow/composite-action `run:` block, every script under `ci/`, and every `.py`/`.sh`/`.bash` file under a `skills/` or `tools/` directory or under `.claude/` (Markdown skill bodies are not parsed). Python is read by AST, following a loop's calls into same-module helpers and through a `gh(*args)` wrapper that builds `["gh", *args]`.

| Shape | Result |
| --- | --- |
| A `while`/`until` loop that sleeps and reaches a GitHub read (`gh api` GET, `gh pr checks`, `gh pr view`, `gh run view`, `gh run list`, or curl/wget/requests/urllib against `api.github.com`) with no bound | violation |
| `gh run watch`, `gh pr checks --watch`, or `watch ... gh ...` anywhere | violation |
| Every read the loop reaches carries a bound: `since=`, `created>=`/`updated>=`/`--created`, or `If-None-Match`/`If-Modified-Since`/ETag | pass |
| A counted `for` loop that sleeps around a read (a retry or a poll), or a sleeping `while` loop whose reads go through a non-literal command | `needs_review` |
| A loop with no sleep (pagination, iteration over input), or a `gh api` write (`-X POST`, fields without `-X GET`, a GraphQL mutation) | not a finding |

A same-line `# ci-lint: allow GHAPI-001 <reason>` on the loop's opening line or on the read excuses it. A loop whose own text names a GitHub App check, in a file GATE-012 scans, is left to GATE-012 so one wait is reported once.

## Linux jobs do not wait on the Linux gate

"Gate first, then fan out" exists to keep a red Linux run from spending a scarce macOS, Windows or ARM runner. It does not apply to a Linux job: a Linux runner is the cheap one, so making it `needs:` the Linux gate only serializes the gate onto the PR critical path. A Linux job therefore starts beside the gate. When the `needs:` edge carries only deterministic, event-derived values (CI mode, SHA, ref), the job re-derives them itself with the same script the gate uses (for example `ci/ci_mode.py`). Keep the `needs:` edge only when the job consumes the upstream job's artifacts, its cache writes, or a non-deterministic output, and keep gating non-Linux jobs on the Linux gate as before (`GEN-024`, [#83](https://github.com/zackees/ci.yml/issues/83)).

Evidence ([zackees/kernal-api#369](https://github.com/zackees/kernal-api/pull/369)): kernal-api's single Linux Dylint job had `needs: linux`, and the 2m17s gate ran before the 9m27s Dylint job. PR run 36346780139 took **12m00s**. After Dylint re-derived its mode and SHA and dropped the edge, both jobs started in the same second, and PR run 36514594793 took **9m27s** (-2.5 min) with the same coverage.

## Trailing aggregate jobs and the runner-queue hop (GEN-025)

**Decision ([#86](https://github.com/zackees/ci.yml/issues/86)):** a job that only aggregates results (checks `needs.*.result`, asserts a pass ran, a few seconds of work) and runs *after* the real work must not add a runner-queue hop to the PR critical path when a work job can carry it. Such a job waits for a free runner after its dependencies finish, and that wait depends on account-wide runner pressure, not on the repository. Measured on zackees/kernal-api's `Dylint coverage` sentinel (`needs: [linux, dylints]`, `if: always()`, ~3 s of work): 37 s (run 36514594793), 1m53s (run 36520421024, `main`), and 2m52s on PR #374 (run 36522485518) -- ~40% of that run's 7m31s.

Prefer, in order:

- **(b) Fold the aggregation into the last step of the slowest work job.** The owner's decision for kernal-api ([kernal-api#375](https://github.com/zackees/kernal-api/pull/375)): the Dylint job's lint step fails on any failed lane and asserts the workspace pass ran, and `linux` keeps its own check.
- **(a) Require the work jobs directly.** A single non-matrix job with no `if:` cannot be silently skipped, so it can be a required check on its own.

A separate aggregate job is still justified -- and is not a `GEN-025` finding -- when it is the repository's single stable required check over many jobs or matrix legs whose names or count vary with the plan: the `CI OK` / `ci-lint gate` aggregator described above (TEST-001's skipped-job check, `GEN-011`'s required check name, `GEN-021`'s verified-reuse consumer). That job exists to turn a plan-dependent job set into one check name, which no single work job can do. Even then, it should be the *only* trailing hop: do not chain a second sentinel (e.g. a per-tool coverage aggregate) in front of or beside it; fold that into a work job or into the gate's own inputs. Option (c), running `ci-lint gate` as a step inside an existing job, is acceptable where one job already needs every other required job.

## Gating jobs carry only consumed work (PERF-002)

When a test or exec lane `needs:` a job, every step in that job sits on the PR critical path. Such a job contains only the work its dependent lanes consume: the build and the artifact, bundle or cache write they read. Work that nothing downstream consumes, such as `cargo clippy`, lint or doc generation ahead of the bundle step, moves to a sibling job that runs in parallel. `GEN-024` removes `needs:` edges that are only for ordering. This rule covers the other case: the edge is real, but the job behind it does extra work.

Two limits apply. First, a split-out sibling that shares the gating job's cache namespace (same `cache-key-suffix`) restores only, with `save-cache: "false"`. Otherwise two jobs race to write one immutable key and the loser's outputs are lost (`CACHE-003`, [#125](https://github.com/zackees/ci.yml/issues/125)). Second, leave a step in place when moving it costs more runner time than it saves. For example, doc-tests take seconds in the build job because everything is already compiled there, but a fresh job would recompile. If a repository keeps unconsumed work in a gating job on purpose, it records why. Measure each change with `PERF-001`'s critical-path figure before and after.

Evidence: in zackees/clud's Build job, Clippy ran for 41 s before the bundle that the unit lane `needs:`. [zackees/clud#1615](https://github.com/zackees/clud/pull/1615) moved it to its own job: Build went from 247-284 s to 222 s, and workflow wall time from about 550 s to 497 s (run 36687468185), at the cost of one extra 134 s runner (`PERF-002`, [#151](https://github.com/zackees/ci.yml/issues/151)).

## Sharding CPU-bound test suites (TEST-003)

To parallelize a CPU-bound test suite, split it across jobs. Do not add in-process workers on one runner. A hosted "4 vCPU" runner has two physical cores with SMT, so a serial CPU-bound run already uses both cores. In zackees/clud, `pytest -n auto` (pytest-xdist) made the 1,573-test pytest phase **slower: 172 s vs ~135 s serial** (zackees/clud#1614, run 36687465340). Summed per-test time grew to 335 s, 2.5x the serial cost, with an average concurrency of ~1.95 on 4 workers. The parallel run also exposed load-sensitive tests. Splitting the suite across jobs worked (zackees/clud#1619: `rust`, `py1of2`, `py2of2`). Total CPU work stays the same, so each extra job adds only its setup time (~20-30 s).

A sharded lane must prove that its shards together run the whole suite, with no test dropped or run twice:

1. **Pure assignment.** Compute shards with a pure function of (collected tests or files, weights, shard count), such as longest-processing-time assignment over per-file weights taken from a real JUnit report (clud's `ci/unit_shard_weights.json`). Shards are then disjoint and complete by construction. A stale weight costs only balance and can be refreshed from any run's JUnit XML.
2. **Every shard gated.** Name every shard in the `CI OK` aggregator and in any release gate, so a skipped, renamed or dropped shard fails closed and does not leave the gate green with part of the suite unproven. For a matrix over shards, the gate requires every leg.
3. **In-process workers need evidence.** Use pytest-xdist, `--numprocesses` or an equivalent on one runner only with recorded serial-utilization evidence: `sum(test time) / wall` and physical vs logical `nproc` for the serial run, with the ratio well below the physical core count (~0.5). This is a measured result for CPU-bound suites, not a ban: an I/O-bound suite may benefit. Larger hosted runners (8+ vCPU) have not been measured.

## Performance rule

The initial candidate threshold is **at least five completed ordinary PR samples in a rolling 30-day window**, with either a **75th-percentile required job execution time over 10 minutes** or a **75th-percentile required PR critical path over 15 minutes** on two successive scans. These are policy starting points to calibrate against fleet data, not claims about current fleet performance. A single severe outlier can be sent for review, but should not automatically become a confirmed timing violation. This rule (`PERF-001`) is distinct from `ci_lint perf compare` (round-5, [docs/ci-toml.md](ci-toml.md#perf-compare-round-5)): that command compares one repository's own benchmark numbers between two runs (non-gating unless a suite opts in with a threshold); it does not compute or enforce a fleet-wide PR-timing percentile, so it does not implement `PERF-001`.

Measure the elapsed time from the first required workflow's creation to the last required check's completion as the PR critical path. Also report per-workflow, job, and step durations. Keep runner queue time separate from execution time; parallel workflow durations must not be added together. Label cache state as cold, warm, or unknown only when run evidence supports the label. Compare new commits with new commits and exact-commit reruns with reruns.

An exception must name the repository, rule ID, reason, owner, compensating coverage, and review date. The documented Soldr dependency cycle in `zackees/running-process` is an example to evaluate for an exception. Exceptions are reviewed when their date arrives or the dependency changes; they do not erase historical findings. `ci.toml`'s `[[exceptions]]` array implements this mechanically for a `ci_lint`-checked repository (`rule`, `path`, `reason`, `issue`, `expires` -- `CT-005` fails an expired entry).

Each confirmed violation gets one issue keyed by repository, rule ID, and workflow or job identity. Update that issue with new evidence rather than creating duplicates. Close it only after the repository passes the rule on current configuration and required checks still run, or after a reviewed policy change or exception is recorded.
